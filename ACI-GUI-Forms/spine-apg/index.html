Spine Access Policy Group

The Create Spine Switch Policy Group dialog lives at Fabric > Access Policies > Switches > Spine Switches > Policy Groups. Its APIC class is infraSpineAccNodePGrp, distinguished name uni/infra/funcprof/spaccnodepgrp-{name} (Cisco DevNet Terraform resource aci_spine_switch_policy_group). This hub and the nine child pages cover the policy names requested for this page set. Only 2 of those nine — BFD IPv4 Policy and BFD IPv6 Policy — are documented as fields of the spine switch policy group. The other 7 are documented as leaf-only on the Access Switch Policy Group. Each child page either shows the spine-side form or states that the field is not present, and links to the matching leaf APG page.

Multi-Site, Multi-Pod and Remote Leaf

Cisco’s guides for Multi-Site, Multi-Pod and Remote Leaf use spine interface access policies for the links toward the inter-site or inter-pod network. They are documented here so that this hub is not confused with those procedures. Sources are listed at the bottom of this page.

Two different “spine policy groups”

  • Spine Switch Policy Group (this page) — class infraSpineAccNodePGrp, path Fabric > Access Policies > Switches > Spine Switches > Policy Groups. Node-level policies: BFD IPv4 and IPv6 instance policies, a spine CoPP profile, a spine CoPP pre-filter profile, and CDP and LLDP interface policies for the management port (Cisco DevNet Terraform; Cisco APIC Support for CDP and LLDP, from APIC 4.2(1)).
  • Spine Access Port Policy Group — class infraSpAccPortGrp (Cisco Ansible module aci_interface_policy_spine_policy_group). Path in the Multi-Site and Nexus Dashboard guides: Fabric > Access Policies > Interface Policies > Policy Groups > Spine Policy Groups > Create Spine Access Port Policy Group. This is the object those guides use for spine ports that face the Inter-Site Network (ISN) or inter-fabric network.

A third, unrelated object also appears in the same guides: a Pod policy group under Fabric > Fabric Policies > Pods > Policy Groups, which must be attached to the default Pod profile before a site is added to Multi-Site or Nexus Dashboard. That is a fabric-policy object, not an access switch policy group.

Multi-Site (ISN / intersite)

The Cisco Multi-Site Orchestrator Deployment Guide, Release 3.3(x), chapter “Configuring Cisco ACI Sites”, and the Cisco Nexus Dashboard 4.2.1 article “Preparing ACI Fabrics”, tell you to configure fabric access policies on each site APIC as you would for a bare-metal host, but for the spine interfaces that connect to the ISN (the Nexus Dashboard article also calls this the inter-fabric network).

  • Create a VLAN pool used for the spine-to-ISN sub-interfaces. The Nexus Dashboard article states that Layer 3 sub-interfaces tagging traffic with VLAN 4 connect the spine switches to the inter-fabric network, and that the pool is created with static allocation and a single VLAN 4 encap block.
  • Create an Attachable Access Entity Profile (AEP) and an external routed domain.
  • Create a Spine Access Port Policy Group. In the Create Spine Access Port Policy Group window the guides specify: Name (for example Spine1-PolGrp); Link Level Policy for the link between the spine switch and the ISN; CDP Policy; and Attached Entity Profile (the AEP created earlier). No additional changes such as security domains are required, per those guides.
  • Create a Spine Interface Profile (Interface Policies > Profiles > Spine Profiles) with a spine access port selector. The guides use example interface ID 5/32 and bind it to the policy group just created.
  • Create a Spine Profile (Switch Policies > Profiles > Spine Profiles) with a spine selector (example node block 201) and attach that interface profile.

The Multi-Site and Nexus Dashboard guides reviewed for this page do not list BFD, Spanning Tree, PoE, Fibre Channel or monitoring as fields of that Spine Access Port Policy Group, and they do not say to create an infraSpineAccNodePGrp object as part of the ISN procedure. Whether a site also applies a Spine Switch Policy Group through the same spine profile was not collected from those guides.

Multi-Pod (IPN)

The Cisco APIC Layer 3 Networking Configuration Guide, Release 6.2(x), section “Multi-pod fabric setup”, describes preparing an existing physical pod to communicate over the interpod network (IPN) and adding a new pod. Beginning with Cisco APIC Release 4.0(1), a GUI wizard under Fabric > Inventory > Quick Start > Add Pod is the documented method.

In Configure Interpod Connectivity you choose spine IDs, enter the spine switch interface (slot and port) used to connect to the IPN, an IPv4 gateway address and mask, and an MTU between 1500 and 9216 bytes. The underlay toward the IPN is OSPF in releases before 5.2(3). From 5.2(3) the underlay can be OSPF or BGP. You also configure an external TEP pool that must not overlap the internal TEP pool or other pods’ external TEP pools, and a data-plane TEP IP with a /32 mask. When you later add a pod you assign a unique Pod ID and a Pod TEP pool, and again identify the IPN-facing spine interfaces.

The 6.2(x) wizard procedure does not name a Spine Switch Policy Group or a Spine Access Port Policy Group as a manual pre-step. Whether the wizard creates those interface or switch policy-group objects was not independently collected from a post-wizard APIC inventory in this work.

Remote Leaf / remote access

The same 6.2(x) Layer 3 guide, chapter “Remote Leaf Switches”, and the Nexus Dashboard 4.2.1 preparing-fabrics article, describe remote leaf switches as leaf nodes that connect to the ACI main data centre through a generic Inter-Pod Network (IPN). They do not have local spine switches or APICs. They establish connections back to spine nodes in the main ACI data centre and are integrated into an existing pod, operating like a standard leaf switch in that pod.

Before a fabric that contains remote leaf switches can be added to Nexus Dashboard or Multi-Site Orchestrator, Cisco requires:

  • Routable subnets for the pod associated with the remote leaf nodes, reachable through the IPN.
  • DHCP relay on the Layer 3 routers connecting to the remote leaf switches, with the routable IP addresses of the Cisco APIC nodes.
  • Enable Remote Leaf Direct Traffic Forwarding, at System > System Settings > Fabric Wide Settings. The Nexus Dashboard article states that you cannot disable this option after you enable it, and that once it is enabled “the spine switches will install Access Control Lists (ACLs) to prevent traffic coming from remote leaf switches from being sent back, since the remote leaf switches will now send directly between each remote leaf switches' TEPs.” There may be a brief disruption while tunnels are built between the remote leaf switches.

The remote-leaf sections reviewed here do not list fields of infraSpineAccNodePGrp as a required remote-leaf step. A binding from a spine switch profile selector to a Spine Switch Policy Group is documented separately (Cisco APIC Support for CDP and LLDP: infraRsSpineAccNodePGrp on infraSpineS). Whether that binding is required for Remote Leaf was not collected.
