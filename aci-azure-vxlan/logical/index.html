Logical topology

Logical topology

How Network ATC intents on the Azure Local host become VLANs, EPGs and bridge domains on ACI, how storage stays Layer 2, and how an optional Border Gateway translates ACI VNIDs toward a remote NX-OS EVPN site.

Example values. VLAN IDs 1600, 1601, 1602, 1611 and 1612 and the two anycast subnets are the paper’s Table 5 and Table 6 examples. The later GUI procedure also uses vlan-107 and vlan-207 for Storage-A and Storage-B.

Host network intents

Microsoft classifies Azure Local traffic as management (north-south administration such as Remote Desktop, Windows Admin Center and Active Directory), compute (to and from virtual machines) and storage (SMB, including Storage Spaces Direct and SMB-based live migration). Storage traffic is Layer 2 and is not routed. Network ATC applies those intents on the host; you should not build SET by hand with New-VMSwitch.

SET is the only teaming technology Azure Local supports. It teams up to eight symmetric adapters and is the only teaming method that works with RDMA adapters and Dynamic VMMQ. Other methods such as LBFO are not supported. Guest RDMA is not supported on Azure Local. InfiniBand is not supported. RDMA works as iWARP or RoCE, and an adapter only interworks with adapters that speak the same protocol.

Source: Microsoft Learn: Host network requirements for Azure Local, Network traffic types, SET, RDMA and Guest RDMA

Storage isolation

The white paper and Microsoft Learn agree that Storage A and Storage B should use different VLANs (and different subnets). Figure 7 of the paper puts VLAN 10 toward Leaf1 and VLAN 20 toward Leaf2 so RoCEv2 stays on the ToR. Microsoft’s four-node example shows how putting every storage adapter in one subnet creates extra connections across the MC-LAG between ToRs; splitting the subnets keeps left-side traffic on TOR1 and right-side traffic on TOR2.

The paper’s later GUI procedure binds Storage-A to eth1/11 on both Node-101 and Node-102 (vlan-107) and Storage-B to eth1/12 on both nodes (vlan-207). That is a different binding than Figure 7. This site quotes both and does not pick a silent winner. Table 5’s storage VLANs are 1601 and 1602, which fit the 1600–1699 pool; the procedure’s 107 and 207 do not.

Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Figure 7 and Configure Storage EPGs · Source: Microsoft Learn: Host network requirements for Azure Local, Storage traffic models

Access chain

The design uses a physical domain, not a VMM domain. The paper’s Table 4 chain is:

  • Static VLAN pool HCI_VLAN_pool (VLAN 1600–1699)
  • Physical domain HCI_phys
  • AAEP HCI_AAEP (infrastructure VLAN disabled)
  • LLDP interface policy HCI_LLDP (transmit enabled, DCBXP IEEE 802.1)
  • Priority Flow Control policy PFC-Auto (Auto, so DCBX can advertise PFC)
  • Leaf access port policy group Individual-HCI — type access, not vpc
  • Nodes 101 and 102, ethernet1/11-12

DCB (PFC and ETS) is required for RoCE and optional for iWARP, but Microsoft still requires switches used for storage to implement 802.1Qbb and 802.1Qaz in every scenario because DCB can be used with either RDMA type. A minimum of three CoS priorities is required, and at least one class must be lossless.

MTU figures from the sources, not invented:

  • White paper, physical architecture: ToR MTU 9216. Endpoints control the packet MTU.
  • White paper, SDN appendix: Azure Local servers use a maximum MTU of 9174, so the ToR must be 9174 or higher; the worked example sets 9216 on the L3Out SVIs.
  • Microsoft physical network requirements: SDN encapsulation needs an MTU in the range 1514 to 9174.

Optional BGW path

If a remote NX-OS VXLAN EVPN site must share VRFs or bridge domains with this ACI fabric, dedicated BGW leaves provide the data-plane translation between ACI’s locally assigned VNIDs and the remote EVPN namespace. From ACI 6.1(4) that translation is the normalized VNI you configure when you stretch a VRF or BD through the border gateway set. The stretch does not change how Azure Local attaches to Leaf-101 and Leaf-102.

Source: Cisco APIC L3 guide 6.2(x): ACI border gateway implementation, normalized VNI · Source: Cisco APIC L3 guide 6.2(x): About ACI border gateways, site-local vs common EVPN domain
