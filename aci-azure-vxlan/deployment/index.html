Deployment

Deployment

Ordered steps from the Cisco Azure Local white paper for the ACI fabric side, then the optional Border Gateway steps from the APIC 6.2(x) Layer 3 guide. The paper does not cover bringing the ACI fabric up, installing Azure Local, or the UCS CIMC configuration (see the UCS CVD). After the ACI or NDFC configuration is complete you can install the Azure Local cluster; before you register it, Microsoft’s connectivity validator Invoke-AzStackHciConnectivityValidation can be run on a node or another computer on the same network.

Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Solution Deployment introduction · Source: Cisco UCS C240 M7 Validated Design for Azure Local, UCS server configuration

Example values. Names such as HCI_VLAN_pool, node 101/102 and ethernet1/11-12 are the paper’s demo example. Replace them with your fabric’s values.
These pages are documentation. They are not an instruction to write to an APIC. No APIC write is performed from this site build.

1. Access policies for the Azure Local server ports

  1. Create a static VLAN pool (example name HCI_VLAN_pool) and add the VLAN range used toward the servers (example 1600–1699). Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Create VLAN Pool
  2. Create a physical domain (example HCI_phys) and attach that VLAN pool. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Configure Physical Domain
  3. Create an AAEP (example HCI_AAEP). Uncheck Enable Infrastructure VLAN and Association to Interfaces at creation time; associate interfaces later through the policy group. Attach the physical domain. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Create AAEP
  4. Under Fabric › Fabric Policies › Policies › Global › LLDP policy by default, enable the optional TLVs DCBX, Port Link Aggregation, Port Maximum Frame Size and Port VLAN Name. Port VLAN is already enabled. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Create LLDP policy to enable the required TLVs
  5. Create an LLDP interface policy (example HCI_LLDP): transmit enabled, DCBXP version IEEE 802.1. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Create LLDP Interface Policy
  6. Create a Priority Flow Control policy (example PFC-Auto) and set it to Auto so PFC can be advertised through DCBX. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Create Interface Priority Flow Control Policy
  7. Create a leaf access port policy group (example Individual-HCI) and attach the AAEP, LLDP policy and PFC policy. This is an access (individual) group, not a vPC or port-channel group. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Create Interface Policy Group
  8. Associate that group with the leaf interfaces that face the Azure Local servers (example Node 101–102, ethernet1/11-12) using Interface Aggregation Type Individual. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Associate the Interface Policy Group

2. QoS classes and custom QoS

  1. Configure QoS Level1 for storage: weighted round robin, 50% bandwidth, PFC enabled, No-Drop Cos 4, scope Fabric-wide PFC (IntraTor PFC is also acceptable if traffic stays on the same leaf). Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Configure QoS Classes
  2. Configure QoS Level2 for cluster communication: weighted round robin, 1% bandwidth, PFC unchecked. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Configure QoS Classes
  3. Configure QoS Level3 (default) for VM and management traffic: weighted round robin, 49% bandwidth, PFC unchecked. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Configure QoS Classes
  4. Create a custom QoS policy (example Storage_and_Cluster) with Dot1P classifiers. Align the classifiers with the classes above: Cos 4 → Level1 (storage) and Cos 5 → Level2 (cluster). The paper’s later GUI click-path lists those level labels the other way around; see the note on the logical page. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Configure Custom QoS Policy

Microsoft’s matching generic recommendation, if you are not following the UCS C240 M6 CVD markings, is Priority 3 or 4 for storage (PFC, 50%), Priority 7 for cluster heartbeats (no PFC, 1% at 25GbE or higher and 2% at 10GbE or lower), and Priority 0 for everything else.

Source: Microsoft Learn: Host network requirements for Azure Local, RDMA traffic considerations

3. Tenant EPGs

  1. In tenant HCI_tenant1, create VRF1, bridge domain BD1 with anycast gateway 192.168.1.254/24, application profile AP1, and EPGs Web (VLAN 1611) and App (VLAN 1612). QoS class Level3. Statically link both EPGs to the physical domain HCI_phys and to every Azure Local-facing interface (Node-101/102 eth1/11-12 in the example). Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Table 6 and Configure Tenant EPGs
  2. In tenant common (or another existing tenant), create BD Mgmt in common_VRF with gateway 10.1.1.254/24 and EPG Mgmt on VLAN 1600, QoS Level3. Use Trunk (Native) if the management network is untagged. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Table 5 and Configure a Management EPG
  3. Create BD Storage-A and BD Storage-B in common_VRF: forwarding custom, L2 unknown unicast flood, unicast routing disabled, no subnet. Create EPGs Storage-A and Storage-B, attach custom QoS Storage_and_Cluster, and statically bind the paths. Table 5 uses VLANs 1601 and 1602; the procedure text uses vlan-107 and vlan-207. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Configure Storage EPGs
  4. Create contract Web-to-App in HCI_tenant1 (scope VRF) and add consumer/provider EPGs. Create or consume Allow-Shared-L3Out from common if tenant networks must reach the shared L3Out. The paper does not publish filter entries or the shared L3Out build itself. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Configure Contracts

4. Host and firewall checks

  1. Confirm the host side with Network ATC intents for management, compute and storage rather than a hand-built SET switch. Source: Microsoft Learn: Host network requirements for Azure Local, Switch Embedded Teaming
  2. Allow the firewall flows listed in Microsoft’s Azure Local firewall requirements. Source: Microsoft Learn: Firewall requirements for Azure Local
  3. If you use RoCE, configure PFC and ETS on every hop, including the switches. DCB is required for RoCE and optional for iWARP. Source: Microsoft Learn: Host network requirements for Azure Local, RDMA traffic considerations
  4. Before registering the cluster, run Invoke-AzStackHciConnectivityValidation from a node or another computer on the same network. Source: Cisco Azure Local / Nexus 9000 white paper (ACI and NX-OS modes), Solution Deployment note

5. Optional: ACI Border Gateways toward an NX-OS EVPN site

Skip this section unless you are interconnecting the ACI fabric with a standalone NX-OS VXLAN EVPN site. These steps come from the APIC 6.2(x) Border Gateway chapters, not from the Azure Local paper.

  1. Confirm every node runs the same ACI version, and that the intended BGW leaves are Nexus 9000 FX or later with 32 GB of RAM (not FX2) and are not already tenant L3Out border leaves. Source: Cisco APIC L3 guide 6.2(x): Guidelines and limitations for ACI border gateways
  2. Discover or preconfigure those leaves as the ACI Border Gateway node type. BGW cannot be configured through the NX-OS-style CLI; use the GUI or REST API. Source: Cisco APIC L3 guide 6.2(x): ACI Border Gateways, feature note
  3. Configure a VXLAN Infra L3Out so the BGW nodes can form eBGP underlay adjacencies with the intersite network. Do not connect an ACI BGW back-to-back to an NX-OS BGW. Source: Cisco APIC L3 guide 6.2(x): ACI Border Gateways, Configure a VXLAN Infra L3Out
  4. Assign a unique VXLAN site ID (vxlanSiteId). From APIC 6.1(2) you cannot create the border gateway set without it. Source: Cisco APIC L3 guide 6.2(x): ACI border gateway implementation, VXLAN site ID
  5. Create a border gateway set and give each pod its external anycast data-plane TEP. Source: Cisco APIC L3 guide 6.2(x): ACI Border Gateways, Create border gateway sets
  6. Create a remote VXLAN fabric policy with the loopback of the remote site’s BGW and associate it with the BGW set. You can associate more than one remote fabric with the same set. Source: Cisco APIC L3 guide 6.2(x): ACI Border Gateways, Create remote VXLAN fabrics
  7. Stretch the tenant VRF and, if you need Layer 2 extension, the bridge domain through the BGW set. From ACI 6.1(4) configure a normalized VNI for the remote EVPN namespace; before 6.1(4) the VNIs must match on both sides. In 6.1(1) a stretched VRF had to be unenforced; from 6.1(2) it can be enforced and you can use ESGs. Source: Cisco APIC L3 guide 6.2(x): ACI border gateway implementation, VRF and BD stretch Source: Cisco APIC L3 guide 6.2(x): Guidelines and limitations for ACI border gateways, unenforced vs enforced

The sources I read do not publish a ready-made IP plan for that Infra L3Out or for the remote BGW loopbacks, so those addresses are not invented here. The YAML file uses clearly marked example values only for the site ID, the external TEP and the normalized VNIs.
