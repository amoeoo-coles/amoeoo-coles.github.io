YAML files

The Azure Local white paper never shows YAML. The files below convert its GUI examples into the public Network-as-Code (nac-aci) data model. The optional Border Gateway file is converted from the APIC 6.2(x) BGW chapters and uses clearly marked example addresses, because those chapters do not publish an Azure Local addressing plan.

Example only. This is not a payload to POST at an APIC and it is not taken from a live fabric. Review every name, VLAN, node ID and address before you reuse it. Filter entries and the shared L3Out are named in the paper but not specified, so they are not invented here.

Access policies

Interface policy group type is access, matching the paper’s “individual connections instead of a port-channel or vPC.”

YAML · access policies
# Network-as-Code (nac-aci data model) converted from the Cisco white paper
# "Microsoft Azure Local Connectivity to Cisco Nexus 9000 Series Switches
# in Cisco NX-OS and Cisco ACI Mode", updated 12 December 2024.
#
# The paper shows APIC GUI steps, not YAML. This file restates those objects
# in the public nac-aci schema:
#   https://netascode.cisco.com/docs/data_models/apic/access_policies/ap_leaf_interface_policy_group/
#   https://netascode.cisco.com/docs/data_models/apic/access_policies/qos/
#   https://netascode.cisco.com/docs/data_models/apic/access_policies/lldp_policy/
#
# Example-only: names, node IDs, ports and the VLAN range are the paper's
# Table 4 lab values (nodes 101-102, ethernet1/11-12, HCI_VLAN_pool 1600-1699).
# Do not apply this file to a live fabric without replacing every value.
#
# Important design point from the paper: the two links between each Azure Local
# server and the leaf pair are INDIVIDUAL connections, not a port-channel or vPC.
# The interface policy group type is therefore "access", not "vpc".

---
apic:
  access_policies:
    vlan_pools:
      - name: HCI_VLAN_pool
        allocation: static
        ranges:
          - from: 1600
            to: 1699
            allocation: static

    physical_domains:
      - name: HCI_phys
        vlan_pool: HCI_VLAN_pool

    aaeps:
      - name: HCI_AAEP
        # Paper: uncheck Enable Infrastructure VLAN and Association to Interfaces
        # when the AAEP is first created; associate interfaces later via the
        # interface policy group.
        infra_vlan: false
        physical_domains:
          - HCI_phys

    interface_policies:
      lldp_policies:
        - name: HCI_LLDP
          admin_rx_state: true
          admin_tx_state: true
          # Paper: "Select Enable for Transmit State" and
          # "Select IEEE 802.1 for DCBXP Version."
          dcbxp_version: IEEE
      priority_flow_control_policies:
        - name: PFC-Auto
          # Paper: Create Priority Flow Control Policy named PFC-Auto and
          # select Auto so the PFC state is advertised through DCBX.
          admin_state: auto

    leaf_interface_policy_groups:
      - name: Individual-HCI
        type: access
        lldp_policy: HCI_LLDP
        priority_flow_control_policy: PFC-Auto
        aaep: HCI_AAEP

    leaf_interface_profiles:
      - name: HCI-servers
        selectors:
          - name: eth1-11-12
            policy_group: Individual-HCI
            port_blocks:
              - name: ports-11-12
                from_module: 1
                from_port: 11
                to_module: 1
                to_port: 12

    leaf_switch_profiles:
      - name: leaf-101-102
        interface_profiles:
          - HCI-servers
        selectors:
          - name: nodes-101-102
            node_blocks:
              - name: leafs-101-102
                from: 101
                to: 102

    qos:
      qos_classes:
        # Paper: Level1 for RDMA/storage, traffic marked Cos 4 by Azure Local.
        - level: 1
          scheduling: wrr
          bandwidth_percent: 50
          pfc_state: true
          no_drop_cos: cos4
          pfc_scope: fabric
        # Paper: Level2 for cluster communication, traffic marked Cos 5
        # by Azure Local in the Cisco ACI example (UCS C240 M6 CVD values).
        # Microsoft Learn instead recommends Priority 7 for cluster heartbeats.
        - level: 2
          scheduling: wrr
          bandwidth_percent: 1
          pfc_state: false
        # Paper: Level3 (default) for VM and management traffic, 49%.
        - level: 3
          scheduling: wrr
          bandwidth_percent: 49
          pfc_state: false

# Fabric-wide optional LLDP TLVs (DCBX, Port Link Aggregation, Port Maximum
# Frame Size, Port VLAN Name) are set in the paper under
# Fabric > Fabric Policies > Policies > Global > LLDP policy by default.
# "Port VLAN" is always enabled regardless of that policy.
# I did not find a published nac-aci field for those optional TLVs, so they
# stay as a GUI step on the Deployment page.
#
# The paper says ToR switches are configured for an MTU of 9216 bytes, and
# that the endpoints control the packet MTU. Link-level policy in nac-aci
# exposes speed/auto/FEC, not MTU, so 9216 is not encoded as a YAML field here.

Tenant, EPGs and contracts

Storage VLANs in this file follow Table 5 (1601 and 1602). The procedure later uses 107 and 207 — both values are quoted on the logical page. Management ports use mode native because the paper prefers an untagged management VLAN.

YAML · tenant
# Network-as-Code tenant objects converted from Tables 5 and 6 and the
# "Configure EPGs" / "Configure Custom QoS Policy" GUI steps in the Cisco
# Azure Local / Nexus 9000 white paper (updated 12 December 2024).
#
# Schema references:
#   https://netascode.cisco.com/docs/data_models/apic/tenants/endpoint_group/
#   https://netascode.cisco.com/docs/data_models/apic/tenants/qos_policy/
#
# Example-only: every name, VLAN and subnet is the paper's lab example.
# Do not apply this file without replacing the values.

---
apic:
  tenants:
    - name: common
      vrfs:
        - name: common_VRF
      policies:
        qos:
          - name: Storage_and_Cluster
            # Mapping used here matches the paper's QoS class section:
            # Level1 = storage (Cos 4, PFC), Level2 = cluster (Cos 5, no PFC).
            # The later "Create Custom QoS Policy" GUI steps swap those level
            # labels (level2 with Dot1P 4 for storage, level1 with 5 for
            # cluster). Treat that as a documentation inconsistency and keep
            # the classes aligned with the PFC-enabled Level1 definition.
            dot1p_classifiers:
              - priority: level1
                dot1p_from: 4
                dot1p_to: 4
              - priority: level2
                dot1p_from: 5
                dot1p_to: 5
      bridge_domains:
        - name: Storage-A
          vrf: common_VRF
          # Paper: Forwarding = Custom, L2 Unknown Unicast = Flood,
          # Unicast Routing unchecked. No subnet — storage is L2 only.
          unicast_routing: false
          l2_unknown_unicast: flood
        - name: Storage-B
          vrf: common_VRF
          unicast_routing: false
          l2_unknown_unicast: flood
        - name: Mgmt
          vrf: common_VRF
          subnets:
            - ip: 10.1.1.254/24
      application_profiles:
        # The paper says "select an existing Application Profile (or create
        # a new one)" in common and does not publish its name. HCI-common
        # is an example name for this conversion.
        - name: HCI-common
          endpoint_groups:
            - name: Mgmt
              bridge_domain: Mgmt
              qos_class: level3
              physical_domains:
                - HCI_phys
              # Table 5: VLAN 1600. Mode can be native if the management
              # network is untagged (the paper prefers native VLAN).
              static_ports:
                - pod_id: 1
                  node_id: 101
                  module: 1
                  port: 11
                  vlan: 1600
                  mode: native
                - pod_id: 1
                  node_id: 101
                  module: 1
                  port: 12
                  vlan: 1600
                  mode: native
                - pod_id: 1
                  node_id: 102
                  module: 1
                  port: 11
                  vlan: 1600
                  mode: native
                - pod_id: 1
                  node_id: 102
                  module: 1
                  port: 12
                  vlan: 1600
                  mode: native
              contracts:
                consumers:
                  - Allow-Shared-L3Out
            - name: Storage-A
              bridge_domain: Storage-A
              custom_qos_policy: Storage_and_Cluster
              physical_domains:
                - HCI_phys
              # VLAN: Table 5 lists 1601 (fits HCI_VLAN_pool 1600-1699).
              # The later GUI procedure uses vlan-107 on Node-101/eth1/11
              # and Node-102/eth1/11. This file follows Table 5.
              # Paths below are the procedure's node/port pairs.
              static_ports:
                - pod_id: 1
                  node_id: 101
                  module: 1
                  port: 11
                  vlan: 1601
                  mode: regular
                - pod_id: 1
                  node_id: 102
                  module: 1
                  port: 11
                  vlan: 1601
                  mode: regular
            - name: Storage-B
              bridge_domain: Storage-B
              custom_qos_policy: Storage_and_Cluster
              physical_domains:
                - HCI_phys
              # Table 5: VLAN 1602. Procedure uses vlan-207 on eth1/12 of
              # Node-101 and Node-102.
              static_ports:
                - pod_id: 1
                  node_id: 101
                  module: 1
                  port: 12
                  vlan: 1602
                  mode: regular
                - pod_id: 1
                  node_id: 102
                  module: 1
                  port: 12
                  vlan: 1602
                  mode: regular
      contracts:
        # Table 5: Allow-Shared-L3Out provided by common. The Shared L3Out
        # itself is not configured in the paper.
        - name: Allow-Shared-L3Out
          scope: global
          subjects:
            - name: Subject1
              # The paper does not publish filter entries.
              filters: []

    - name: HCI_tenant1
      vrfs:
        - name: VRF1
      bridge_domains:
        - name: BD1
          vrf: VRF1
          subnets:
            - ip: 192.168.1.254/24
      application_profiles:
        - name: AP1
          endpoint_groups:
            - name: Web
              bridge_domain: BD1
              qos_class: level3
              physical_domains:
                - HCI_phys
              static_ports:
                - pod_id: 1
                  node_id: 101
                  port: 11
                  vlan: 1611
                  mode: regular
                - pod_id: 1
                  node_id: 101
                  port: 12
                  vlan: 1611
                  mode: regular
                - pod_id: 1
                  node_id: 102
                  port: 11
                  vlan: 1611
                  mode: regular
                - pod_id: 1

Optional Border Gateway stretch

Azure Local servers still attach to Leaf-101 and Leaf-102. This file only describes stretching VRF1 and BD1 through a dedicated BGW set so a remote NX-OS EVPN site can use a normalized VNI (ACI 6.1(4) and later). Site ID, data-plane TEP and VNI values are examples.

YAML · BGW examples
# Optional ACI Border Gateway (BGW) objects for interconnecting this ACI
# fabric with a standalone Cisco NX-OS VXLAN EVPN site.
#
# This is NOT part of the Azure Local white paper. Azure Local servers
# attach to regular leaf nodes (Table 4: node-101 and node-102). BGW nodes
# must be dedicated leaves and cannot also be tenant L3Out border leaves
# (Cisco APIC L3 guide 6.2(x), Guidelines and limitations).
#
# Every address, node ID, site ID and normalized VNI below is an EXAMPLE
# for this lab page. The BGW chapters document the objects but do not
# publish a ready-to-use addressing plan for Azure Local.
#
# Beginning with ACI 6.1(4), a normalized VNI translates the VNID that
# APIC assigned locally to the VNID used in the remote EVPN domain.
# Before 6.1(4), VNIs had to be symmetrical across the two fabrics.
#
# Schema:
#   https://netascode.cisco.com/docs/data_models/apic/tenants/border_gateway_set_policy/
#   https://netascode.cisco.com/docs/data_models/apic/tenants/vxlan_vrf_stretch/
#
# Related GUI steps that I did not encode, because the sources do not give
# lab values for them: register the leaf as a BGW node type; configure the
# VXLAN Infra L3Out (eBGP underlay toward the intersite network); configure
# the remote VXLAN fabric (remote BGW loopback). Back-to-back connections
# between an ACI BGW and an NX-OS BGW are not supported.

---
apic:
  tenants:
    - name: infra
      policies:
        border_gateway_sets:
          - name: BGW-set-1
            # EXAMPLE site ID. From APIC 6.1(2) a unique vxlanSiteId is required
            # before you can create the border gateway set.
            vxlan_site_id: 100
            external_data_plane_ips:
              - pod_id: 1
                # EXAMPLE external anycast data-plane TEP for pod 1.
                ip: 10.0.255.1

    - name: HCI_tenant1
      vrfs:
        - name: VRF1
          vxlan_stretch:
            border_gateway_set_policy: BGW-set-1
            # EXAMPLE normalized VNI for the remote EVPN namespace.
            normalized_vni: 50001
      bridge_domains:
        - name: BD1
          vxlan_stretch:
            border_gateway_set_policy: BGW-set-1
            # EXAMPLE normalized VNI for the stretched bridge domain.
            normalized_vni: 50111
