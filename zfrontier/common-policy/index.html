Overview and architecture

Hybrid workforces, distributed applications across private data centers and public clouds, and growing IoT footprints create siloed security domains when campus, WAN, data center, and cloud platforms each maintain independent policy models. Cisco’s Common Policy architecture solves this by using Cisco Identity Services Engine (ISE 3.4 Patch 1) as a central context hub that collects identity and workload metadata, normalizes it into Security Group Tags (SGTs), and distributes IP-to-SGT bindings across domains.

ISE ACI Connector

Builds a direct connection to Cisco APIC to discover Endpoint Groups (EPGs) and Endpoint Security Groups (ESGs) and map their endpoints to SGTs. Campus and non-ACI SGTs shared back to APIC become External EPGs (EEPGs) on an L3Out so ACI contracts enforce policy.

ISE Workload Connector

Connects to on-premises VMware vCenter and public clouds (AWS, Azure, GCP) to import VM and workload attributes and assign primary and secondary SGTs through ordered Workload Classification rules.

pxGrid & SXP Distribution

Publishes normalized IP-to-SGT context over pxGrid to Catalyst Center, SD-WAN Manager, FMC, and APIC, and over SXP to TrustSec listeners such as SD-Access Border Nodes.

Cross-domain enforcement example from the guide: Campus users classified as Employees are permitted by the firewall to reach a data center web-app SGT (while Contractors are permitted to a cloud cloud-app SGT), and APIC simultaneously enforces a consumed/provided contract on the ACI leaf between the Employees EEPG and the web-app EPG.

Multi-site Common Policy topology

The validated test bed spans three autonomous Cisco ACI data center fabrics (two single-pod sites and one Multi-Pod fabric joined by an IPN), an SD-Access Transit and campus sites (Main, Transit, and Branch), a central SD-WAN WAN fabric, a Firepower (FTD) boundary to a Non-SDA TrustSec domain, vCenter workloads, and FMC. The three ACI fabrics connect across Layer 3-only L3Out paths with unique IP subnets per fabric (with L3Out border leaves deployable in both pods of the Multi-Pod fabric). SD-Access Main and Branch sites integrate with SD-WAN Edges via eBGP, VRF-lite, and inline SGT, while ISE PSNs run per-VN SXP connections to the SD-Access Main Border Nodes.

ISE domain integrations

ISE and Cisco ACI integration

ISE 3.4 Patch 1 and ACI 6.1(2) support multiple single-pod or Multi-Pod ACI fabrics, multi-tenant/multi-VRF designs, multiple or shared L3Outs, inter-VRF, cross-fabric ACI context exchange, and learning ACI contracts directly inside ISE.

  • ISE prerequisites: Enable pxGrid and SXP services (Administration > Deployment > Deployment Node), configure DNS to resolve APIC node hostnames, and remove any legacy ACI integration.
  • ACI prerequisites: Pre-configure tenants, VRFs, EPGs/ESGs, L3Outs, and contracts in APIC, and ensure DNS resolves ISE pxGrid hostnames.
  • Setup workflow: Add a Cisco ACI connection under Work Centers > Workload Connections, import APIC certificates to the ISE Trusted Certificate Store if validating certs, choose the SGT naming convention (Connection Name, Tenant, VRF, App Profile, EPG Type), select EPGs/ESGs (leaving none selected leaves the connection suspended), optionally reserve per-DC SGT numbering ranges (e.g. 3100s for DC1, 3200s for DC2), and verify under APIC Integrations > ISE Integrations.

Inbound and outbound SGT domain rules

  • Inbound SGT domain rules: Map incoming IP-SGT bindings from connectors into specific SGT domains. If no inbound rule matches, bindings enter the Default SGT domain (always enabled). For SD-WAN integration, the SGT domain name is matched to the target SD-WAN VPN number (for example, domain 1 maps bindings to SD-WAN VPN 1).
  • Outbound SGT domain rules: By default, ACI learns no context from ISE. Under Work Centers > Inbound & Outbound SGT Domain Rules > Outbound SGT Domain Rules, administrators select a target ACI connection and L3Outs, match SGT domains and SGT names (such as Employees, Contractors, Developers, or SGTs learned from another ACI fabric), and attach Consumed and Provided Contracts. ISE automatically creates the matching EEPGs on the chosen ACI L3Outs and binds the contracts.

Workload connectors and classification flow

ISE connects to VMware vCenter (and AWS, Azure, or GCP) via Work Centers > Integrations > Workload Connections to import workload IPs and metadata attributes (such as guest OS type or tags). Administrators then build ordered rules under Work Centers > Workload Connectors > Workload Classification.

Classification rules assign a primary SGT and optional secondary SGTs to external workloads. The primary SGT is labeled Security Group in the pxGrid session topic and is the tag used to publish IP-to-SGT mappings over SXP. Secondary SGTs are published on the pxGrid session topic as an ordered array named Secondary Security Groups. When multiple rules match and specify primary SGTs, only the first matched rule’s SGT acts as the primary SGT; subsequent matched rules’ primary SGTs are appended in rule-execution order to the end of the secondary list alongside those rules’ secondary SGTs. Inbound SGT domain rules assign the resulting IP bindings to their target SGT domains. Note that for any workload learned from a Cisco ACI connection, the primary SGT is always the SGT derived from its EPG or ESG.

Catalyst Center, SD-WAN Manager, and FMC

  • Catalyst Center: Configured as the TrustSec Policy Administration Point (PAP); security groups, access contracts, and policies become read-only in ISE while Catalyst Center authors them.
  • SD-WAN Manager: Integrated from Administration > Integration Management > Identity Services Engine (supported since SD-WAN 20.10.1 / IOS XE 17.10.1a). SGTs are sent to SD-WAN Manager for policy authoring and IP-SGT mappings go to SD-WAN Controller (verified via show idmgr pxgrid-status, which shows SXP websocket connection to /topic/com.cisco.ise.sxp.binding on port 8910).
  • Secure FMC: Integrated via pxGrid 2.0 (supported since FMC 6.7) under Integration > Identity Sources > Identity Services Engine. ISE pushes subscribed ACI EPG/ESG SGTs and bindings to FMC for FTD enforcement.

Policy enforcement points

ACI leaf policy enforcement

Campus 802.1X/MAB IP-SGT bindings learned by ISE are pushed to ACI via Outbound SGT domain rules, creating EEPGs on the L3Out. Policy control enforcement direction is set to Ingress (default) or Egress on the ACI VRF. In the guide’s example, the Employees EEPG consumes contract ALLOW_WEB_SSH (TCP 22, 80, 443) provided by the WEB EPG; if data center endpoints also initiate connections to campus, a reverse Provided/Consumed contract is added.

SD-Access Border Nodes

To filter outbound campus-to-DC traffic on SD-Access Border Nodes, ISE PSNs push ACI-learned IP-SGT bindings over per-VRF SXP sessions. Border Nodes act as SXP listeners (campus host bindings already arrive at ISE via RADIUS from SD-Access Edge Nodes), and CTS role-based enforcement is enabled on the SVIs facing the fusion router.

SD-WAN Edge

Inbound SGT domain rules route IP-SGT bindings to matching SD-WAN VPN numbers (e.g., SGT domain 1 maps to VPN 1), distributed by SD-WAN Controller over OMP. On SD-WAN Manager, create a Unified Security Policy (Configuration > Security > Add Unified Security Policy) with an NG Firewall rule using an Identity destination list (selecting the SGT), apply it to the service VPN zone pair, and attach the Security Policy to the device template.

Firewall Threat Defense (FTD)

Once FMC integrates with ISE over pxGrid 2.0, Access Control Policy rules can match SGTs directly under the Dynamic Attributes tab (for example, permitting Contractors, Developers, and Employees to ACI-learned DB_prod_EPG). Verification uses FTD packet-tracer (displaying src sgt / dst sgt and sxp source type in the Snort firewall phase) and FMC Analysis > Connection Events > Table View.

Workload reports and troubleshooting

ISE Workload Reports display workloads received from ACI and vCenter along with how each IP-SGT binding was classified, and can be exported for auditing. For campus-to-data-center troubleshooting, the guide defines a four-step verification flow:

  1. Verify campus host SGT assignment: On the SD-Access Edge switch, run show authentication sessions interface gigabitEthernet 1/0/1 details and confirm the returned SGT Value and VRF.
  2. Check ISE IP-SGT bindings: Confirm that valid IP-to-SGT bindings exist in ISE for both the campus endpoint and the data center workload.
  3. Check ACI EEPG bindings: Verify the campus host IP appears inside the target ACI EEPG’s SGT bindings on the L3Out.
  4. Verify ACI contracts: Confirm that matching Consumed and Provided contracts are attached to the EEPG and destination EPG respectively.
