What this is

A tenant in ACI is a policy container, not a routing domain. The VRF is the routing domain, the bridge domain holds the subnet, and the EPG is where endpoints and contracts attach. Those three objects do not have to live in the same tenant. This page describes four placement patterns that show up often when a fabric is shared by one operations team, or by several application teams.

The diagrams are original. They are not copies of a conference slide. Object names such as vrf-01 and app_dev are teaching names used in the models, not names from a live fabric.

Named relations in ACI (bridge domain to VRF, EPG to bridge domain, EPG to contract) are resolved by name in the current tenant first, then in tenant common. If a user tenant and tenant common both have a VRF called vrf-01, a typo or a deletion in the user tenant can silently bind objects to the common VRF. In production, prefix names in common so they cannot collide. That behaviour is described in Cisco’s ACI policy-model documentation, linked under Sources.

Nothing on this page was written to an APIC. The models use only documentation IPv4 ranges (192.0.2.0/24, 198.51.100.0/24 and 203.0.113.0/24). Credentials are placeholders ({{ apic_host }}, {{ apic_username }}, {{ apic_password }}). Do not apply these models to a shared Always-On APIC unless you have written approval.

“Route leak” here means advertising a subnet into another VRF. Endpoints that already share a VRF (patterns A–C in these models) still need a contract when the VRF is enforced, but they do not need a shared-scope subnet for that communication.

Pattern A — everything in tenant common

The VRF, the bridge domains and their subnets, and the application profile with its EPGs all live in the built-in common tenant. This suits a fabric that one operations team owns, where splitting edit rights between teams is not the main goal. Because objects in common can be used by name from every other tenant, a change here has fabric-wide reach.

Scenarios

A1 — Single operations team. The VRF is enforced and the preferred group is disabled, so EPGs talk only through a contract. This is the default in the model (terraform plan -var='scenario=a1', or the Ansible default).

Tenantcommon (built-in, not created or deleted)

BD subnetsbd-web 192.0.2.1/24 and bd-app 198.51.100.1/24 · scope private
L2 unknown unicastHardware Proxy (proxy)
EPGepg-web (consumer) and epg-app (provider) in ap-ops, preferred group not used
Contract / scopectr-web-to-app · scope tenant · TCP/80 filter
Security domain / RBACsec-ops is created but is not attached to tenant common

A2 — Small lab on the same layout. The objects are the same, but the VRF preferred group is enabled and the EPGs are included in it, so they can talk without the contract. A1 and A2 are alternatives for the same VRF; do not apply both at once.

SettingValue in this model
Tenantcommon
VRFvrf-01 · enforced · preferred group enabled

When to use it. A single team already operates the fabric, and you want the fewest moving parts. Avoid this pattern when several teams need independent edit rights: almost everyone who can change common can change everyone else’s networking.

RBAC and security domains. Restricting the built-in common tenant is an APIC administrative decision. These models do not attach a security domain to common, and they never delete that tenant.

Contracts and leaking. All endpoints in this pattern share one VRF, so a contract is enough. A subnet does not need to be marked shared unless you later leak it to another VRF.

Ansible and Terraform excerpts (full files are under models/a/):

- name: Create VRF in tenant common
  cisco.aci.aci_vrf:
    host: "{{ apic_host }}"
    username: "{{ apic_username }}"
    password: "{{ apic_password }}"
    tenant: common
    vrf: vrf-01
    policy_control_preference: enforced
    preferred_group: disabled
    state: present
locals {
  common_dn = "uni/tn-common"
}
resource "aci_vrf" "common" {
  parent_dn                       = local.common_dn
  name                            = "vrf-01"
  policy_control_enforcement_mode = "enforced"
}
resource "aci_application_epg" "web" {
  parent_dn = aci_application_profile.ops.id
  name      = "epg-web"
  relation_to_bridge_domain = {
    bridge_domain_name = aci_bridge_domain.web.name
  }
}

Pattern B — VRF and bridge domains in common, EPGs in the user tenant

A network team keeps the VRF and the subnets in tenant common. Application teams get their own tenants and only create application profiles and EPGs, which bind to those common bridge domains. Any tenant can use any of those shared subnets, which is useful when addressing is central, and risky if a team binds to the wrong BD.

Scenarios

B1 — Central addressing, two application teams. Tenants app_web and app_data each have an EPG bound to a BD in common. A contract in common with scope context lets them communicate inside the shared VRF.

SettingValue in this model
Tenantscommon (VRF and BDs) · app_web · app_data
VRFvrf-01 in common · enforced · preferred group disabled
BD subnetsbd-web 192.0.2.1/24 and bd-app 198.51.100.1/24 in common · scope private
L2 unknown unicastHardware Proxy
EPGepg-web in app_web, epg-data in app_data, each bound to a common BD by name
Contract / scopectr-web-to-app in common · scope context
Security domain / RBACsec-app-web and sec-app-data, attached to the user tenants in Terraform

B2 — Shared services on the same addressing. A third user tenant, app_shared, provides an HTTP contract (also in common, scope context) that epg-web consumes. The provider EPG still uses a common BD. This is additive with B1 in the same model.

SettingValue in this model
TenantsSame as B1, plus app_shared
VRFSame shared vrf-01 in common
BD subnetsepg-shared binds to bd-app in common · scope private
L2 unknown unicastHardware Proxy
EPGepg-shared in app_shared (provider)
Contract / scopectr-shared-http in common · scope context
Security domain / RBACsec-app-shared attached to app_shared in Terraform

When to use it. You want one IP plan and one VRF, but you still want application teams to manage only their EPGs and contracts bindings.

RBAC and security domains. Give each user tenant its own security domain. Keep write access to common with the network team. Remember that an EPG in a user tenant can still attach to any named BD in common.

Contracts and leaking. Scope context is the right contract scope when the EPGs already share a VRF but live in different tenants. Subnets stay private in this model. If two teams share a BD, they also share that L2 segment, so isolation has to come from contracts (and from not placing endpoints that should be apart on the same BD).

- name: Create EPGs that bind to bridge domains in tenant common
  cisco.aci.aci_epg:
    host: "{{ apic_host }}"
    username: "{{ apic_username }}"
    password: "{{ apic_password }}"
    tenant: "{{ item.tenant }}"
    ap: "{{ item.ap }}"
    epg: "{{ item.epg }}"
    bd: "{{ item.bd }}"
    state: present
  loop: "{{ user_tenants }}"
  # Named relations resolve in the current tenant first, then in common.
resource "aci_application_epg" "web" {
  parent_dn = aci_application_profile.web.id
  name      = "epg-web"
  relation_to_bridge_domain = {
    bridge_domain_name = aci_bridge_domain.web.name
  }
}
resource "aci_aaa_domain_relationship" "web" {
  aaa_domain_dn = aci_aaa_domain.web.id
  parent_dn     = aci_tenant.app_web.id
}

Pattern C — VRF in common, bridge domains and EPGs in the user tenant

The VRF still lives in tenant common, so every user tenant can attach a bridge domain to it. Subnets, though, are created in the user tenant. Another tenant cannot simply reuse those subnets. This is a natural split between a shared routing domain and team-owned addressing — for example a development tenant and a test tenant that should not share prefixes.

Scenarios

C1 — Dev and test, shared VRF, separate subnets. Tenants app_dev and app_test each have their own BD and private subnet, both attached to vrf-01 in common.

SettingValue in this model
Tenantscommon (VRF only) · app_dev · app_test
VRFvrf-01 in common · enforced · preferred group disabled
BD subnetsbd-dev 192.0.2.1/24 in app_dev · bd-test 198.51.100.1/24 in app_test · scope private
L2 unknown unicastHardware Proxy
EPGepg-dev in app_dev, epg-test in app_test, each bound to its local BD
Contract / scopeNone required for C1 isolation; C2 adds one
Security domain / RBACsec-app-dev and sec-app-test, attached in Terraform

C2 — Selected communication inside the shared VRF. A contract in common with scope context is provided by the test EPG and consumed by the dev EPG. Because both BDs already sit in the same VRF, the subnets stay private; this is not an inter-VRF leak.

SettingValue in this model
TenantsSame as C1
VRFSame shared vrf-01
BD subnetsStill private in each user tenant
L2 unknown unicastHardware Proxy
EPGSame EPGs
Contract / scopectr-dev-to-test in common · scope context · TCP/80
Security domain / RBACSame as C1

When to use it. Several teams should share a routing domain (and maybe a shared L3Out later) but must keep their own prefixes. It is also a reasonable way to split development and test without giving each team a separate VRF.

RBAC and security domains. Teams can be allowed to edit their tenant (BDs, subnets, EPGs) and still be denied write access to the VRF in common.

Contracts and leaking. Same-VRF, cross-tenant traffic uses a contract of scope context. Mark a subnet shared only if you also need to advertise it into a different VRF. That step is not part of this model.

- name: Create a bridge domain in each user tenant, bound to the common VRF
  cisco.aci.aci_bd:
    host: "{{ apic_host }}"
    username: "{{ apic_username }}"
    password: "{{ apic_password }}"
    tenant: "{{ item.tenant }}"
    vrf: vrf-01
    bd: "{{ item.bd }}"
    state: present
  loop: "{{ user_tenants }}"
resource "aci_bridge_domain" "dev" {
  parent_dn = aci_tenant.dev.id
  name      = "bd-dev"
  relation_to_vrf = {
    vrf_name = aci_vrf.common.name
  }
}
resource "aci_subnet" "dev" {
  parent_dn = aci_bridge_domain.dev.id
  ip        = "192.0.2.1/24"
  scope     = ["private"]
}

Pattern D — everything in the user tenant

Each team gets a complete stack: tenant, VRF, bridge domain, subnet and EPG. This is the usual choice when more than one team uses the APIC and you want RBAC to line up with the policy boundary. Isolation is the default. Connecting tenants is then an explicit shared-services design, not an accident of a common VRF.

Scenarios

D1 — Two application teams, fully isolated. Tenants app_a and app_b each have a dedicated VRF and a private subnet. There is no communication between them until D2 is added.

SettingValue in this model
Tenantsapp_a · app_b
VRFvrf-app-a and vrf-app-b · enforced · preferred group disabled
BD subnetsbd-a 192.0.2.1/24 and bd-b 198.51.100.1/24 · scope private
L2 unknown unicastHardware Proxy
EPGepg-a and epg-b in their own application profiles
Contract / scopeNone between the two tenants in D1
Security domain / RBACsec-app-a and sec-app-b, each attached to its tenant in Terraform

D2 — Shared services between tenants. Tenant shared_svc has its own VRF and a subnet at 203.0.113.1/24 with scope shared (and public in the Terraform model, so it can also be advertised to an L3Out later). It provides a contract of scope global, which is exported into app_a and app_b for those EPGs to consume. D2 is additive with D1 in the same model.

SettingValue in this model
Tenantsapp_a · app_b · shared_svc
VRFEach tenant keeps its own VRF
BD subnetsshared_svc bd-shared 203.0.113.1/24 · scope shared (and public in Terraform)
L2 unknown unicastHardware Proxy
EPGepg-shared provides the contract; app EPGs consume the exported interface
Contract / scopectr-shared-http in shared_svc · scope global · exported as ctr-shared-http-if
Security domain / RBACsec-shared attached to shared_svc in Terraform

When to use it. Multiple teams, a requirement for clear RBAC, or a design where shared services should be called out as their own tenant rather than objects in common.

RBAC and security domains. Map each tenant to a security domain, then map each team’s APIC users to that domain. That is the main reason to choose this pattern.

Contracts and leaking. Inter-VRF shared services need both a contract of scope global and a provider subnet marked shared. Exporting the contract (Ansible aci_contract_export, Terraform aci_imported_contract) gives the consumer tenant a local interface to bind to. A contract that stays in common is an alternative that this model does not use, to keep the D boundary intact.

- name: Export the shared-services contract into each application tenant
  cisco.aci.aci_contract_export:
    host: "{{ apic_host }}"
    username: "{{ apic_username }}"
    password: "{{ apic_password }}"
    tenant: shared_svc
    contract: ctr-shared-http
    destination_tenant: "{{ item.tenant }}"
    name: ctr-shared-http-if
    state: present
  loop: "{{ app_tenants }}"
resource "aci_subnet" "shared" {
  parent_dn = aci_bridge_domain.shared.id
  ip        = "203.0.113.1/24"
  scope     = ["public", "shared"]
}
resource "aci_contract" "shared" {
  tenant_dn = aci_tenant.shared.id
  name      = "ctr-shared-http"
  scope     = "global"
}

Models and downloads

Each pattern folder has an Ansible playbook and vars file, a Terraform root module, and a Network-as-Code style data YAML. A zip of the whole set is at downloads/aci-tenant-design-patterns-models.zip. Read models/ and models/README.md before you run anything.

PatternFolderWhat the model creates
Amodels/a/Objects under tenant common, plus security domain sec-ops (not attached to common)
Bmodels/b/Common VRF and BDs, tenants app_web, app_data and app_shared, contracts in common
Cmodels/c/Common VRF, tenants app_dev and app_test with their own BDs, contract in common
Dmodels/d/Tenants app_a, app_b and shared_svc, global contract export

YAML in these models was checked with a Python parser. Each Terraform root was passed through terraform fmt and terraform validate against CiscoDevNet/aci 2.22.0. The playbooks were not applied to an APIC, so a live run may still fail on fabric-specific policy or on a newer or older schema. Associating a security domain with a tenant is shown in Terraform (aci_aaa_domain_relationship). The cisco.aci 3.0.0 module list on this site includes aci_aaa_domain but not a dedicated module for that relationship, so the Ansible playbooks create the domain object only.
