Multi-VRF Firewall Insertion

v1 · 25 Nov 2026, 7:58 PM AEDT

This hidden page describes a two-VRF firewall service-insertion design for Cisco ACI. Each VRF is its own Layer 3 routing and security domain. Inside a VRF, an application endpoint group consumes a contract from a database endpoint group, and policy-based redirect steers the matching traffic through a firewall. The three diagrams are original drawings. They are not copies of a vendor or third-party figure. The Ansible series that follows is a numbered, data-driven example and has been syntax-checked only.

Overview

The design uses two VRFs, named VRF-1 and VRF-2 in the example objects. Traffic stays inside the VRF that sourced it. Nothing is leaked or shared between the two VRFs unless a later design explicitly adds that path — this page does not.

In each VRF an Application EPG acts as the consumer: it starts the conversation. A Database EPG acts as the provider: it offers the service. A contract names the permitted traffic, through a subject and a filter. The subject is also bound to a service graph. When the contract is applied, the fabric can redirect matching flows to a firewall before they reach the provider, and again on the return path.

Policy-based redirect (PBR) is the insertion method used here. The graph node is a routed, go-to firewall function in redirect mode. The consumer-side connector points at the firewall’s external interface and a next-hop in the application bridge domain. The provider-side connector points at the internal interface and a next-hop in the database bridge domain. The firewall itself still permits or denies the session according to its own policy; the fabric only steers the packets to it.

VLANs 301 and 302 belong to VRF-1 (consumer and provider). VLANs 303 and 304 belong to VRF-2. A single physical firewall appliance is attached to the leaf pair on Port-Channel 1, built as a vPC in the example. That appliance is presented to the fabric as two logical devices, one per VRF, each with an External and an Internal interface.

Example only. Node IDs, ports, the vPC protection group, subnets, firewall interface IPs and MAC addresses on this page are illustrations. Production port-channel, vPC, VLAN and firewall interface details depend on the service-insertion design actually used in that fabric.

Physical topology

The fabric sketch shows an example spine pair and the leaf pair 101 and 102. Those two leaves form an explicit vPC protection group. Eth1/1 on both leaves is a member of vPC Port-Channel 1, which is the attachment to the firewall. Application and database servers sit on example access ports: Eth1/10 and Eth1/11 on each leaf. Interface and node identifiers are labelled as examples.

Logical topology

The tenant holds both VRFs, but each VRF remains an independent routing and security domain. Inside a VRF the application bridge domain and EPG sit on the consumer side, the database bridge domain and EPG sit on the provider side, and the contract with its service graph sits between them. The redirect path is the same in both VRFs: consumer EPG to the firewall’s external interface, through the firewall, then from the internal interface to the provider EPG. A divider down the middle marks the isolation: this example has no inter-VRF contract, no shared service or leaked route.

Example IP addressing

The table and the drawing use private RFC1918 subnets so the playbooks have concrete values to consume. They are not a production addressing plan. Each bridge domain has a gateway on the .1 address. The firewall interface in that bridge domain uses a .10 address. The PBR destination is that interface IP, with a placeholder MAC address.

Ansible series

Run the playbooks in this order. Steps 01–06 would change fabric policy if they were pointed at an APIC. Step 07 only queries. Do not run any of them against a production APIC.

  1. 01-access-policies.yml — static VLAN pool 301–304, physical domain, AAEP, vPC Po1 and server access ports.
  2. 02-tenant-vrf-bd.yml — tenant, two VRFs, four bridge domains and example subnets.
  3. 03-app-profile-epg.yml — application profile, EPGs, domain bindings and example static paths.
  4. 04-l4l7-device.yml — logical and concrete firewall devices and their External/Internal interfaces.
  5. 05-pbr-redirect.yml — PBR policies and example next-hop destinations.
  6. 06-service-graph-contract.yml — filter, contract, service graph, device selection and EPG bindings.
  7. 07-validate.yml — read-only queries, including an aci_rest GET of the tenant tree.

The series is data-driven. Object names, VLANs, example subnets and PBR destinations live in YAML model files under vars/ and group_vars/. The playbooks loop over those models rather than hard-coding each object twice. Login values stay as placeholders: the password is always {{ apic_password }} and is never stored in this repository.

The modules used here are from the cisco.aci collection version 3.0.0, checked with ansible-doc. The destination module name is aci_l4l7_policy_based_redirect_destination (singular). Every playbook in the series was passed with ansible-playbook --syntax-check. Nothing was run against an APIC.

How to use the playbooks

The files are also published as downloads under ansible/. From that folder, with the cisco.aci collection installed, syntax-check every playbook before considering a lab run:

Login values are not stored in the repository. group_vars/apic.yml sets apic_host to apic.example.invalid and leaves apic_password unset. If you ever run a playbook in a lab, pass the values on the command line or from an untracked file, for example:

07-validate.yml is the only playbook that is written as a read-only query. Playbooks 01–06 are examples of policy that would be created, and are not meant to be applied to a production fabric. Certificate verification defaults to enabled (apic_validate_certs: true).

This series was syntax-checked with Ansible core 2.22.0 and cisco.aci 3.0.0. All seven playbooks returned a passing syntax-check.
