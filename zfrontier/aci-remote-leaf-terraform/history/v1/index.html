ACI Remote Leaf Terraform, Nexus IPN & Nexus Dashboard Orchestrator

v1 · 26 Nov 2026, 4:00 PM AEDT

Browser-only Cisco ACI Remote Leaf workbench with 32 interactive forms that live-generate Terraform HCL for the CiscoDevNet/aci, CiscoDevNet/mso (Nexus Dashboard Orchestrator, platform = "nd") and CiscoDevNet/nxos providers, plus ready-to-paste NX-OS CLI. Covers Remote Leaf TEP pools, DHCP relay, OSPF/BGP to the IPN, vPC remote leaf pairs, Direct Traffic Forwarding, and Remote Leaf with Multi-Pod or Multi-Site. Includes original diagrams, an indicative BOM, rack and cabling plans, Day 1 / Day 2 / BAU / troubleshooting, a YAML sample model, Before-Push terraform plan previews, and a CI/CD + NetBox 4.x sync pack.

Offline & credential-safe by design: Everything renders locally in your browser; this page never contacts an APIC, Nexus Dashboard, or IPN switch. Generated .tf files always use variables (var.apic_password, var.ndo_password, var.nxos_password) or CI placeholders ({{ apic_password }}, {{ ndo_password }}) and documentation/lab prefixes. The plan panel is a browser preview (+ to add, ~ to change). A real terraform fmt / validate / plan / apply runs only on a self-hosted runner.
YAML data model: published at data/sample.yml and consumed in Terraform with yamldecode(file("${path.module}/data/sample.yml")).
Forms start with built-in defaults (same values as the sample file).

3.3 Step-by-Step Cabling, Labelling, Power and Airflow

  1. Print two labels per cable before seating optics, using the scheme in the table (device-port at both ends).
  2. Seat spine–IPN 100G LR4 links first, then IPN–remote-leaf LR4 links (rows 1–8). Confirm light on both ends before moving on.
  3. Cable the remote-leaf vPC peer-link and keepalive next, then access ports in each hall.
  4. Cable OOB last, onto a management VRF/switch that does not transit VLAN-4. Documentation prefix 203.0.113.0/24 is an example only.
  5. Power: land A and B feeds on separate PDUs. Circuit amperage, breaker size and UPS runtime are not collected.
  6. Airflow: this sketch assumes port-side intake / front-to-rear exhaust. Confirm each PID’s airflow SKU before ordering; reversed-airflow units are not collected.
  7. Leave slack loops, strain-relieve MPO/LC, and photograph each rack after labelling for the as-built pack (not published here).
  8. Do not trunk server VLANs onto the IPN switches. The IPN carries OSPF and DHCP relay (and optional WAN BGP); it is not a server leaf.
  9. Do not power the remote leaves until IPN OSPF and DHCP relay to the APIC TEPs have been verified.

4. Planning & Prerequisites

Lock the fabric TEP pool, a non-overlapping Remote Leaf TEP pool, IPN /30s and jumbo MTU before commissioning any remote leaf. Confirm the pool managed object with moquery -c fabricSetupP — this page does not invent that DN.

Planning tree

Step-by-step planning guide

  1. Choose a Remote Leaf TEP pool that does not overlap the fabric TEP, external TEP or IPN prefixes.
  2. Assign VLAN-4 /30s between every spine and each IPN switch, and between each IPN and each remote leaf.
  3. Confirm jumbo MTU end-to-end and that DHCP relay on the IPN can reach the APIC infra addresses.
  4. Load the sample model or type values, then copy the generated .tf into the automation repo.

5. Design Patterns (Terraform per Pattern)

Each pattern has its own Terraform module/config. A recommended remote site is a vPC leaf pair with no local spines or APICs. Direct Traffic Forwarding is optional and version-specific in its exact behaviour.

Design patterns

Step-by-step design guide

  1. Start with a vPC remote leaf pair and an explicit protection group.
  2. Decide whether to enable Direct Traffic Forwarding after reading the prerequisites for your ACI release.
  3. If the fabric is Multi-Pod, associate the RL pool with one pod — not a second APIC cluster.
  4. If the fabric is in Multi-Site, each APIC cluster still owns its own remote leaves.

6. Nexus IPN Switch Configs (NX-OS CLI & CiscoDevNet/nxos)

Bring the IPN underlay and DHCP relay up before powering the remote leaves. Each form emits Terraform and paste-ready NX-OS.

IPN bring-up

Step-by-step IPN bring-up

  1. Enable features and jumbo MTU, create VRF ACI-IPN and Loopback0.
  2. Build VLAN-4 subinterfaces toward every spine and every remote leaf, then OSPF in that VRF.
  3. Configure DHCP relay on the RL-facing subinterfaces to the APIC infra TEPs.
  4. Run the verify form (OSPF FULL, MTU, relay) before commissioning the remote leaves.

7. Day 1 — Remote Leaf Pool, Registration, vPC, ND/NDO

Create the Remote Leaf TEP pool (after confirming the MO), register the nodes, create the vPC group, and optionally onboard the same fabric to Nexus Dashboard Orchestrator as one site.

Day 1 order

Step-by-step Day 1

  1. Complete IPN OSPF and DHCP relay first.
  2. Create the Remote Leaf TEP pool from the APIC GUI, or with aci_rest_managed after you confirm the DN with moquery -c fabricSetupP.
  3. Register both remote leaf serials and bring up the vPC protection group.
  4. Finish the Nexus Dashboard cluster out of band if you use NDO, then apply mso_site once for the fabric.

8. Day 2 — Tenant, VRF, BD, EPG, Contracts and NDO Deploy

Day 2 objects are fabric-wide, including endpoints behind the remote leaves. Use the ACI provider directly, or declare them in an NDO template and deploy to the single fabric site.

Day 2 objects

Step-by-step Day 2

  1. Create the tenant and VRF, then the BD and subnet.
  2. Add an application profile, EPG and contract, and bind the EPG to a domain on the remote leaf interfaces (domain DN is not collected unless you add it).
  3. If NDO owns the policy, deploy the template to the single fabric site.

10. Troubleshooting (Show, moquery, terraform state)

Read-only diagnostics for DHCP/TEP, IPN OSPF, Direct Traffic Forwarding and Terraform state/import. These forms do not declare write resources.

Diagnostics

Step-by-step diagnostic order

  1. If a remote leaf has no TEP, check IPN DHCP relay and reachability to the APIC infra TEPs first.
  2. If OSPF stays in EXSTART, compare MTU on both ends of VLAN-4.
  3. If TEPs exist but traffic hairpins unexpectedly, confirm whether Direct Traffic Forwarding is enabled and whether your release’s prerequisites are met.
  4. If Terraform drifts from the GUI, use terraform plan and terraform import with the real ID or serial — do not invent import IDs.
