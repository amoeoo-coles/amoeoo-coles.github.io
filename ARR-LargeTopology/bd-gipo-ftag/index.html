BD GIPo, VRF GIPo and FTAG trees

v1 · 15 Nov 2026, 10:48 PM AEDT

How ARR-FABRIC forwards multi-destination traffic: the BD GIPo, the VRF GIPo, and the FTAG trees that carry them. The worked example is Cursor_Tenant6_VRF and Cursor_Tenant6_BD. Fabric values are taken from the Cursor_Tenant6 v4 post-check (15 November 2026, 12:47 AM AEDT) and the hw-monitor IS-IS snapshot at 14 Nov 2026, 10:08 PM AEDT. No APIC was contacted for this page. Where a value was not in those files, it is marked not collected. Example addresses used only to show the FTAG encoding are labelled as examples.

In one sentence. Each bridge domain gets a /28 outer multicast address (the BD GIPo) for Layer 2 floods of its VNID. Each VRF can get a separate /28 (the VRF GIPo) for user multicast when PIM is enabled. The ingress leaf hashes the flow onto one FTAG tree and writes that FTAG into the low four bits of the GIPo, which becomes the outer destination IP of the VXLAN packet.

Walkthrough

Unicast in ACI is a leaf-spine-leaf VXLAN tunnel between VTEPs, described on the VXLAN page. Multi-destination traffic — broadcast, unknown unicast that is still flooded, and multicast — cannot use a single unicast VTEP as the outer destination. ACI instead encapsulates the frame as a multicast VXLAN packet whose outer destination is a GIPo (Group IP outer address) and forwards that packet along a loop-free FTAG tree built by IS-IS.

BD GIPo

When a bridge domain is created, the APIC allocates it a /28 block from the fabric GIPo pool. The APIC GUI and fvBD.bcastP show the base address of that block, with the last four bits zero. On ARR, Cursor_Tenant6_BD has bcastP 225.0.42.48. That address is tied to the BD's VNID, 16547722 (fvBD.seg, operationally l2BD.fabEncap).

Traffic that uses the BD GIPo is Layer 2 flood traffic for that VNID:

  • Broadcast, including ARP when arpFlood is yes (it is, on this BD).
  • Link-local multicast (224.0.0.0/24), which is always flooded in the BD.
  • Unknown unicast, but only when the BD floods it. Cursor_Tenant6_BD has unkMacUcastAct=proxy, so unknown unicast is sent to the spine proxy and is not flooded on the BD GIPo.
  • IP multicast, when PIM is not enabled on the BD. mcastAllow is no here, so IP multicast also uses the BD GIPo.

VRF GIPo

The official 6.2(x) Tenant Routed Multicast guide says the APIC allocates one GIPo for the VRF and one GIPo for every BD under that VRF. A GIPo may be shared among BDs or among VRFs, but not mixed between the two. For the same VRF, the VRF GIPo is common to IPv4 and IPv6.

The VRF GIPo is used when a BD has multicast routing (PIM or PIM6) enabled:

  • All user multicast on that BD, Layer 2 and Layer 3, is forwarded on the VRF GIPo.
  • Broadcast and unknown-unicast flood on that same BD still use the BD GIPo.

The APIC GUI displays a GIPo for every VRF, always as a /28 base. The collected fvCtx for Cursor_Tenant6_VRF has the VRF VNID (seg 2818049) but no bcastP. Cisco Community guidance reads the VRF GIPo from pimCtxP.vrfGipo, and only when PIM is enabled on the VRF. That class was not pulled. The value is therefore not collected (needs read-only APIC pull).

The default fabric pool is 225.0.0.0/15, entered at APIC setup and then permanent. VRF GIPos come from that same pool. A community example shows pimCtxP.vrfGipo 225.1.192.0/3. I am not treating 225.1.192.0/xx as a reserved default VRF range: the official 6.2(x) page describes /28 allocations from the fabric pool, and the /3 display in that example is not explained in the official guide.

FTAG trees

The outer GIPo /28 has sixteen addresses, selected by the low four bits of the last octet. The ingress leaf picks an FTAG by hashing the flow, then adds that FTAG to the GIPo base to form the outer destination IP. Cisco's TAC note and Cisco Live BRKDCN-3900 give the same rule: if the GIPo is 225.0.0.0 and the FTAG is 0x9, the outer destination is 225.0.0.9; if the GIPo is 225.0.2.128 and the FTAG is 0x8, it is 225.0.2.136. On this BD, the labelled example is 225.0.42.48 + FTAG 5 = 225.0.42.53. The TAC note also says the hash is not stable even for the same leaf and the same BD GIPo, so FTAG 5 here is an example, not a captured flow.

There are 16 FTAG IDs (0–15) because of those four bits. On ARR, isisFmcastTree shows FTAGs 0–12 active and 13–15 inactive with root 0.0.0.0, which matches Cisco's own CLI examples (FTAG 0–12 enabled, 13–15 disabled) and the TAC note that the hash is in the range 0 to 12. FTAG 0 is active but marked usage=internal; FTAGs 1–12 are usage=user. Cisco ACI Fundamentals says the fabric "supports up to 12 FTAGs". That wording is slightly tighter than the 0–12 range in the TAC and Cisco Live material; both are recorded here rather than forced into one number.

Each active tree has one root. The APIC places those roots on spines at fabric bring-up. Multiple trees may share a spine, which is the ARR case: from every leaf, FTAGs 0–4, 11 and 12 are rooted on SPINE-201 (10.0.8.65) and FTAGs 5–10 on SPINE-202 (10.0.8.66). IS-IS recomputes the tree after a topology change, so a leaf can reach the same root through another path if an uplink fails. Root placement itself is configuration-driven and is not moved automatically when a spine fails. A non-root spine still takes part: its rootPort points at a leaf used to reach the root spine. That is visible on SPINE-201 for FTAGs 5–10, and on SPINE-202 for FTAGs 0–4, 11 and 12.

ARP flood walk

This is the path an ARP request from N9Kv-01 would take if the access path were formed. It is the forwarding mechanism, not a packet capture. In the 15 November 2026, 12:47 AM AEDT post-check every fvRsPathAtt was unformed, and no vlanCktEp for VLAN 1601 or 1603 was present. N9Kv-01 is the intended host on LEAF-101 eth1/5 VLAN 1601; N9Kv-03 is the intended host on LEAF-103 eth1/5 VLAN 1603. The BD itself is already instantiated on all four leaves.

  1. N9Kv-01 sends an ARP request with a broadcast destination MAC into LEAF-101 eth1/5, VLAN 1601, in Cursor_Tenant6_BD.
  2. LEAF-101 classifies the frame into that BD, hashes the flow, and encapsulates VXLAN with VNID 16547722. In this example the hash selects FTAG 5, so the outer destination is 225.0.42.53 and the outer source is the LEAF-101 TEP 10.0.8.64.
  3. The leaf forwards the packet on its FTAG 5 root port (eth1/54 toward SPINE-202 in the collected tree).
  4. SPINE-202 is the root of FTAG 5 (rootPort unspecified on that spine). It forwards on the tree's outgoing interfaces except the incoming link, so the packet goes to the other leaves and is not sent back to LEAF-101.
  5. LEAF-102, LEAF-103 and LEAF-104 receive the packet, decapsulate it, and flood the inner ARP in the BD on any local ports that belong to it.
  6. If the LEAF-103 path were formed, N9Kv-03 would see the ARP. LEAF-102 and LEAF-104 also have the BD instantiated, so they receive the flood even when no host is up there.

What this does not show. The FTAG chosen for a real ARP from N9Kv-01 is not known. Unknown unicast on this BD is proxy, so a unicast frame to an unknown MAC would not follow this flood. The IS-IS GIPo route table in the 14 Nov 2026, 10:08 PM AEDT snapshot does not yet list 225.0.42.48, because that pull was taken before the BD appeared as l2BD on the leaves (createTs 11:00 PM AEDT on 14 November 2026 on LEAF-101). The FTAG roots themselves are fabric-wide and were the same in the 7:20 PM, 9:44 PM and 10:08 PM AEDT pulls that evening.
