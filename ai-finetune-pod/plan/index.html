Plan: AI FineTune Pod on RTX 4000 SFF Ada

A phased plan from bare hardware to a served, monitored, fine-tuned model. It runs on Docker throughout. Memory figures are estimates based on published minimums. Example files are labelled as examples and use placeholders for every version and secret.

Example values. Image tags such as <YY.MM>, model paths and every <REPLACE> are placeholders. Hyperparameters are starting points, not tuned results.

Downloads

docker-compose.ymltrain config YAML

Phases

P0 · Scope and data inventory

Pick 2–3 target tasks (see Showcase). List the data sources: ACI/NaC YAML from the lab repos and a NetBox export. Decide what must never leave the box (credentials, tokens, customer data).

P1 · Hardware and host

Choose a chassis with a free PCIe x16 slot (PCIe 4.0 for full bandwidth), the right bracket height and good front-to-back airflow over a dual-slot card.

P2 · OS, driver and containers

Linux, NVIDIA driver, Docker and the NVIDIA Container Toolkit, then a GPU smoke test in a container.

P3 · Data prep

Turn YAML and NetBox objects into chat-format Q&A JSONL, then dedupe, scrub secrets and split train/eval.

P4 · Training

Run a QLoRA baseline on a 7–8B instruct model, then iterate on LoRA rank, sequence length and epochs.

P5 · Evaluation

Use a held-out question set, scripted exact-match and YAML-validity checks, and side-by-side review against the base model.

P6 · Export and serve

Merge the adapter, export GGUF (llama.cpp/Ollama) or keep safetensors for vLLM, and serve locally.

P7 · Monitoring and ops

Feed nvidia-smi and DCGM exporter metrics into the existing Grafana. Back up adapters and datasets, and version runs.

1 · Hardware and host selection

  • Slot. The card is PCIe 4.0 x16. Use an x16 slot wired for Gen 4 so host-to-GPU loading isn’t throttled. Source: NVIDIA RTX 4000 SFF Ada Generation datasheet (PDF, Apr 2023)
  • Size and bracket. It’s 2.7” H × 6.6” L, dual slot. A reseller listing says both low-profile and full-height brackets ship with it. Check the bracket that comes with your unit. Source: NVIDIA RTX 4000 SFF Ada Generation datasheet (PDF, Apr 2023) Source: NVNexus reseller listing: NVIDIA RTX 4000 SFF Ada Generation
  • Power. Total board power is 70 W. A reseller says there’s no auxiliary power connector, so no PCIe power cable is needed. Size the PSU for the CPU and drives, with the card’s 70 W on top. Source: NVIDIA RTX 4000 SFF Ada Generation datasheet (PDF, Apr 2023) Source: NVNexus reseller listing: NVIDIA RTX 4000 SFF Ada Generation
  • Airflow. The card uses an active cooler. In SFF cases, keep the intake clear in front of the fan and exhaust out the back, and avoid sandwiching it against another card. Source: NVIDIA RTX 4000 SFF Ada Generation datasheet (PDF, Apr 2023)
  • Host RAM and disk estimate. Model downloads, checkpoints and merged outputs add up fast. Plan for fast NVMe with hundreds of GB free, and at least as much system RAM as the largest model you will merge in 16-bit. This is a planning rule of thumb, not a vendor figure.

2 · OS, NVIDIA driver, CUDA and Container Toolkit

Install the NVIDIA driver from your distribution’s package manager, as NVIDIA recommends. Then install the NVIDIA Container Toolkit and register it with Docker using nvidia-ctk runtime configure --runtime=docker. Inside containers, CUDA comes from the image (for example NGC PyTorch), so the host only needs the driver. Source: NVIDIA Container Toolkit install guide Source: NVIDIA NGC: PyTorch container

CLI · example
# Example host bring-up (Ubuntu). Commands as documented by NVIDIA; adjust versions.
nvidia-smi                                   # driver loaded, card visible, 20GB listed
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
docker run --rm --gpus all nvcr.io/nvidia/pytorch:<YY.MM>-py3 nvidia-smi
docker run --rm --gpus all --ipc=host nvcr.io/nvidia/pytorch:<YY.MM>-py3 \
  python -c "import torch;print(torch.cuda.get_device_name(0), torch.cuda.is_bf16_supported())"

NGC’s docs say PyTorch containers may need more shared memory. Use --ipc=host or --shm-size. Source: NVIDIA PyTorch container release notes: Running PyTorch

3 · Docker stack

Pick one trainer image and stick with it per experiment.

  • NGC PyTorch + Hugging Face PEFT/TRL: the most transparent option, with LoRA adapters from PEFT and SFTTrainer from TRL. Source: NVIDIA NGC: PyTorch container Source: Hugging Face PEFT documentation Source: Hugging Face TRL documentation
  • Unsloth: an official unsloth/unsloth Docker image, with memory-saving kernels for QLoRA and LoRA. Source: Docker Hub: unsloth/unsloth image Source: Unsloth docs: Requirements and fine-tuning VRAM table
  • Axolotl: YAML-driven fine-tuning if you prefer config files over Python. Source: Axolotl documentation

The example compose file below has three profiles: train, serve and an always-on dcgm-exporter.

docker-compose.yml · example
# EXAMPLE ONLY - docker-compose.yml for the AI FineTune Pod.
# Replace every <REPLACE> value. Pin image tags you have tested; do not run :latest in production.
# Requires: NVIDIA driver + NVIDIA Container Toolkit configured for Docker (nvidia-ctk runtime configure --runtime=docker).
name: ai-finetune-pod

x-gpu: &gpu
  deploy:
    resources:
      reservations:
        devices:
          - driver: nvidia
            count: 1
            capabilities: [gpu]

services:
  trainer:
    <<: *gpu
    image: nvcr.io/nvidia/pytorch:<YY.MM>-py3     # NGC PyTorch; or unsloth/unsloth:<tag>
    ipc: host                                    # NGC docs: raise shared memory (--ipc=host or --shm-size)
    working_dir: /workspace
    volumes:
      - ./data:/data:ro                          # prepared JSONL datasets (read-only)
      - ./models:/models                         # base models + merged outputs
      - ./ckpt:/ckpt                             # checkpoints and LoRA adapters
      - ./configs:/configs:ro
    environment:
      HF_HOME: /models/hf-cache
      HF_TOKEN: ${HF_TOKEN:-}                    # only for gated models; keep in .env, never commit
    command: ["bash", "-lc", "pip install -q peft trl bitsandbytes datasets && python /configs/train.py --config /configs/qlora-train.example.yaml"]
    profiles: ["train"]

  serve:
    <<: *gpu
    image: vllm/vllm-openai:<tag>
    ipc: host
    volumes:
      - ./models:/models:ro
    command: ["--model", "/models/merged/<REPLACE-model-dir>", "--max-model-len", "4096", "--gpu-memory-utilization", "0.85"]
    ports:
      - "127.0.0.1:8000:8000"                    # local only; put a reverse proxy + auth in front if shared
    profiles: ["serve"]

  dcgm-exporter:
    <<: *gpu
    image: nvcr.io/nvidia/k8s/dcgm-exporter:<DCGM_EXPORTER_TAG>
    cap_add: ["SYS_ADMIN"]                       # per NVIDIA DCGM Exporter install docs
    ports:
      - "9400:9400"                              # Prometheus scrape target for the existing Grafana
    restart: unless-stopped

4 · What fits in 20GB

QLoRA keeps the base model frozen in 4-bit NF4 and trains small LoRA adapters in bf16. The QLoRA paper fine-tuned a 65B model on a single 48GB GPU. LoRA trains low-rank adapters on a 16-bit base. Source: Dettmers et al., QLoRA: Efficient Finetuning of Quantized LLMs (arXiv 2305.14314) Source: Hu et al., LoRA: Low-Rank Adaptation of Large Language Models (arXiv 2106.09685) The QLoRA and LoRA columns are Unsloth’s published minimums. They are not measured on this card, and real use grows with context length and batch size. The fit column is my estimate for a 20GB card.

Model sizeQLoRA 4-bit min (Unsloth)LoRA 16-bit min (Unsloth)Fit on 20GBWhy
0.5B——Full fine-tune possible estimateHugging Face: about 18 bytes/param for mixed-precision AdamW, so ≈ 9 GB plus activations Source: Hugging Face Transformers: Model training anatomy (memory per parameter)
1B——Full fine-tune borderline estimate≈ 18 GB before activations at 18 bytes/param, so too tight; use LoRA Source: Hugging Face Transformers: Model training anatomy (memory per parameter)
3B3.5 GB8 GBQLoRA or LoRA estimateBoth under 20GB at Unsloth minimums Source: Unsloth docs: Requirements and fine-tuning VRAM table
7B5 GB19 GBQLoRA (LoRA 16-bit marginal) estimate16-bit LoRA minimum is within 1 GB of the card’s 20GB Source: Unsloth docs: Requirements and fine-tuning VRAM table
8B6 GB22 GBQLoRA only estimate16-bit LoRA minimum exceeds 20GB Source: Unsloth docs: Requirements and fine-tuning VRAM table
14B8.5 GB33 GBQLoRA only estimateLeaves the most headroom for context in the 7–14B range Source: Unsloth docs: Requirements and fine-tuning VRAM table
27B22 GB64 GBDoes not fit estimateQLoRA minimum exceeds 20GB Source: Unsloth docs: Requirements and fine-tuning VRAM table
Rule of thumb, an estimate. On this card, use QLoRA for roughly 7–14B models and LoRA for ≤3B. Full fine-tuning is only for sub-1B models, because Hugging Face counts about 18 bytes/param for mixed-precision AdamW (6 for weights, 8 for optimizer states, 4 for gradients) before activations. Source: Hugging Face Transformers: Model training anatomy (memory per parameter) Source: Unsloth docs: Requirements and fine-tuning VRAM table

5 · Dataset prep

  1. Collect ACI/NaC YAML (tenants, VRFs, BDs, EPGs, contracts) from the lab repos, and a read-only NetBox export (sites, devices, prefixes, VLANs). Use read-only access only. No APIC or NetBox writes.
  2. Scrub secrets before anything else: passwords, tokens, keys, .env contents and admin emails. Keep the scrub log.
  3. Generate Q&A pairs, for example “Which BD is EPG X in, and what subnet?” or “Write the NaC YAML for a new EPG in tenant Y.” Answers are taken from the real files, never made up.
  4. Format as chat-style JSONL (messages), dedupe, and split 90/10 into train/eval with no overlap between them.

The QLoRA authors found that dataset quality and fit to the task mattered more than size. Source: Dettmers et al., QLoRA: Efficient Finetuning of Quantized LLMs (arXiv 2305.14314)

6 · Training

Start with a QLoRA baseline using the example config below: NF4 4-bit, double quantization, bf16 compute, LoRA on all linear layers and a paged optimizer. The QLoRA paper found that putting adapters on all linear layers was the key to matching 16-bit results. It also introduced paged optimizers to absorb memory spikes. Source: Dettmers et al., QLoRA: Efficient Finetuning of Quantized LLMs (arXiv 2305.14314) Source: Hugging Face Transformers: bitsandbytes quantization

qlora-train.example.yaml · example
# EXAMPLE ONLY - QLoRA training config for a 20GB card (illustrative values, not tuned).
# Read by an example train.py built on Hugging Face Transformers + PEFT + TRL (SFTTrainer).
run_name: aci-nac-qa-qlora-<YYYYMMDD>
base_model: /models/<REPLACE-7B-or-8B-instruct-model>
output_dir: /ckpt/aci-nac-qa-qlora

quantization:            # QLoRA: 4-bit NF4 base weights + double quantization, bf16 compute
  load_in_4bit: true
  bnb_4bit_quant_type: nf4
  bnb_4bit_use_double_quant: true
  bnb_4bit_compute_dtype: bfloat16

lora:
  r: 16
  alpha: 32
  dropout: 0.05
  target_modules: all-linear   # QLoRA paper: adapters on all linear layers matter most

data:
  train_file: /data/aci_nac_qa.train.jsonl   # {"messages":[{"role":"user",...},{"role":"assistant",...}]}
  eval_file: /data/aci_nac_qa.eval.jsonl
  max_seq_length: 2048

training:
  per_device_train_batch_size: 1
  gradient_accumulation_steps: 16
  gradient_checkpointing: true
  learning_rate: 2.0e-4
  lr_scheduler_type: cosine
  warmup_ratio: 0.03
  num_train_epochs: 2
  optim: paged_adamw_8bit      # paged optimizer to absorb memory spikes
  bf16: true
  logging_steps: 10
  eval_steps: 100
  save_steps: 200
  save_total_limit: 3
  seed: 42

7 · Evaluation

  • Use the held-out eval split, never seen in training. Score with exact or regex match for facts like VLAN IDs, subnets and BD names, and use a YAML parser plus the NaC schema for generated configs.
  • Compare against the untuned base model on the same prompts, and record both in the Showcase.
  • Do a human spot check on 20–50 answers before calling a run “good” estimate.

8 · Quantize, export and serve

  • Merge the LoRA adapter into the base model (PEFT), or keep it separate for vLLM’s LoRA support. Source: Hugging Face PEFT documentation Source: vLLM documentation
  • GGUF: convert with convert_hf_to_gguf.py, quantize with llama-quantize (for example Q4_K_M), and run in llama.cpp or Ollama. Ollama can build from Safetensors or GGUF. Source: llama.cpp: convert_hf_to_gguf.py and llama-quantize README Source: Ollama Modelfile reference (build from Safetensors or GGUF)
  • AWQ: AutoAWQ is officially deprecated, and its work moved to vLLM’s llm-compressor, so use that path if you need AWQ for vLLM. Source: AutoAWQ README (deprecated; adopted by vLLM llm-compressor)
CLI · example
# Example export paths (llama.cpp README). Run inside a llama.cpp checkout.
python convert_hf_to_gguf.py /models/merged/aci-nac-qa --outfile aci-nac-qa-bf16.gguf --outtype bf16
./build/bin/llama-quantize aci-nac-qa-bf16.gguf aci-nac-qa-Q4_K_M.gguf Q4_K_M
# Ollama: Modelfile with  FROM ./aci-nac-qa-Q4_K_M.gguf  then  ollama create aci-nac-qa -f Modelfile

9 · Serving

vLLM needs compute capability 7.5 or higher, and this card is 8.9. The example compose file binds vLLM to 127.0.0.1 only. For a lighter desktop-style option, use Ollama or llama.cpp with the GGUF file. Source: vLLM GPU installation (compute capability requirement) Source: NVIDIA CUDA GPUs: compute capability list Source: Ollama Modelfile reference (build from Safetensors or GGUF)

10 · Monitoring into the existing Grafana

NVIDIA’s DCGM Exporter runs as a container on port 9400 and exposes GPU metrics for Prometheus, such as GPU utilisation and framebuffer memory used. Add it as a scrape target and build a GPU panel next to the existing Grafana dashboards. nvidia-smi --query-gpu is the quick fallback. Source: NVIDIA DCGM docs: Install DCGM Exporter Source: NVIDIA nvidia-smi documentation

CLI · example
# DCGM exporter (NVIDIA DCGM docs), then add a Prometheus scrape job for <pod-host>:9400
docker run -d --rm --name dcgm-exporter --gpus all --cap-add SYS_ADMIN \
  -p 9400:9400 nvcr.io/nvidia/k8s/dcgm-exporter:${DCGM_EXPORTER_TAG}
# Quick look without Prometheus:
nvidia-smi --query-gpu=timestamp,temperature.gpu,power.draw,utilization.gpu,memory.used --format=csv -l 5

11 · Integration with the network work

  • Config Q&A: ask “where is EPG X, which contracts does it consume?” and get answers from a model tuned on the AOAPIC/ARR NaC YAML. Link the answers back to the ACI Policy and YAML Model pages.
  • NetBox assistant: natural-language lookups over the NetBox export, such as prefixes, VLANs and devices per site. Read-only.
  • NaC YAML drafting: draft a new tenant or EPG block, then run nac-validate and nac-test before any human-approved push. The model never writes to the APIC.
  • Fault triage notes: summarise Report 17 fault lists into plain-language runbook steps, with links to MONITORING.
