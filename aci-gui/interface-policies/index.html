How they differ

A Leaf Access Port Policy Group (infraAccPortGrp) applies a set of interface policies to one physical port on a leaf. A PC Interface Policy Group (infraAccBndlGrp, lagT=link) applies a set of policies to a port channel: several ports on the same leaf, bundled as one logical interface for more bandwidth and link redundancy.

Cisco’s Layer 2 access-interfaces guide describes the policy group as the named object that holds those interface policies (for example a link-level policy or a storm-control policy) and is then selected on the interface. The same guide’s port-channel chapter describes a port channel as a logical interface that bundles physical interfaces, provides redundancy, and load-balances traffic across the members. Starting with APIC 6.1(3), a port channel can have 32 members; FEX and SAN port-channels stay at 16.

Most policy fields exist on both groups. The important differences are:

  • Port Channel Policy and PC Member Port Policy Groups exist only on the PC group (and on a vPC group). They set LACP or static bundling, and per-member LACP rate or priority.
  • 802.1X Port Authentication, PoE Interface, DWDM and Transceiver policy appear on the Access Port form, not on the DC3 PC form. Cisco also states that 802.1X is not supported on port channels or virtual port channels.
  • On the PC form, several policies sit on a second wizard page titled Advanced Policies. They are the same kind of policy, not a second class of object.

Why the GUI says “Advanced Policies”

On the Create PC Interface Policy Group wizard, the first page holds Name, Description, Attached Entity Profile, CDP, Link Level, LLDP, Port Channel Policy, then CoPP, both data-plane policers, Fibre Channel, L2 Interface, Link Flap and Link Level Flow Control. The second page is titled Advanced Policies. That page holds MACsec, MCP, Monitoring, Port Security, SyncE, the NetFlow Monitor Policies table, the PC Member Port Policy Groups table, Priority Flow Control, Slow Drain, Storm Control and STP. The Cisco Live lab LTRDCN-2143 uses the same two-step wizard and sets MCP on the Advanced Policies page.

Advanced Policies is a collapsed or second-step GUI section for policies that many designs leave at their defaults or unselected. It is not a ranking of importance. MCP, Storm Control and STP BPDU Guard are often recommended on edge ports, even though they sit in that later section on the PC form.

The Create Leaf Access Port Policy Group form on APIC DC3 is a single dialog with a View Advanced Settings disclosure. The walk-through already on this site used that disclosure for MCP and L2 Interface. Other Access fields (802.1X, PoE, Storm Control, STP and the rest) are still on that same form. This note does not invent which of those remaining Access fields sit inside the disclosure.

Policy chain diagram

Two relationships matter. The policy group does not select a port by itself. A leaf switch profile selects the leaf, an interface profile holds a port selector, and that selector points at the policy group. The policy group also points at an AAEP, which points at a domain, which points at a VLAN pool. Cisco’s access-policy troubleshooting guide describes this chain. Hardware comes up after the profiles are in place, but data traffic still needs a tenant application profile, EPG and contract.

Three scenarios

The YAML below is NaC-style, with keys checked against the local Cisco NaC access-policy modules already used on the Access and PC form pages (leaf_interface_policy_groups, aaep, lldp_policy, mcp_policy, port_channel_policy, spanning_tree_policy, storm_control_policy, plus the interface policy lists). Values are illustrative. No live inventory and no real addresses are used. APIC credentials, if a pipeline needs them, stay as placeholders such as {{ apic_password }}.

1. Single-homed device — Access Port Policy Group

A firewall management port, a bare-metal server with one NIC, or a camera attaches to one leaf port. Use a Leaf Access Port Policy Group with an AAEP, LLDP, MCP (and the global MCP instance), STP BPDU Guard and Storm Control. Add 802.1X or PoE only when that device must authenticate or must be powered from the switch.

# Example only. APIC login credentials are not stored here.
# In a pipeline, use placeholders such as {{ apic_username }} / {{ apic_password }}.
# Interface IDs below are illustrative, not a live inventory.
apic:
  access_policies:
    # MCP must also be enabled globally (Fabric > Access Policies >
    # Policies > Global > MCP Instance Policy default). By default MCP is
    # disabled globally and enabled on each port (Cisco APIC Basic
    # Configuration Guide, MCP interface policy).
    mcp:
      admin_state: true
      per_vlan: true
    interface_policies:
      lldp_policies:
        - name: lldp_enabled
          admin_rx_state: true
          admin_tx_state: true
      mcp_policies:
        - name: mcp_enabled
          admin_state: true
      spanning_tree_policies:
        - name: stp_bpdu_guard
          bpdu_guard: true
          bpdu_filter: false
      storm_control_policies:
        - name: storm_control_edge
          # Choose a rate below 100 for the design. Cisco documents that
          # a percentage of 100 means no storm control, and 0 suppresses
          # all of that traffic type. A specific rate is not collected here.
          action: drop
      # Add port_authentication / poe_interface policies only when the
      # attached device needs 802.1X or PoE. Those fields are Access-only.
    leaf_interface_policy_groups:
      - name: Leaf101_Access
        type: access
        aaep: LAB-AAEP
        lldp_policy: lldp_enabled
        mcp_policy: mcp_enabled
        spanning_tree_policy: stp_bpdu_guard
        storm_control_policy: storm_control_edge
    leaf_interface_profiles:
      - name: Leaf101_IntProf
        selectors:
          - name: eth1-1
            policy_group: Leaf101_Access
            port_blocks:
              - from_card: 1
                from_port: 1
                to_port: 1
    leaf_switch_profiles:
      - name: Leaf101
        selectors:
          - name: Leaf101
            node_blocks:
              - from: 101
                to: 101
        interface_profiles: [Leaf101_IntProf]

2. Server with two to four NICs on one leaf — PC Interface Policy Group

The server’s NICs land on the same leaf and should act as one logical link. Use a PC Interface Policy Group with LACP Active, the same AAEP, and the same edge protections (LLDP, MCP, BPDU Guard, Storm Control). The Port Channel Policy is the field that does not exist on the Access group. Member-level LACP rate or priority stays in PC Member Port Policy Groups on the Advanced Policies page, and can be left empty when defaults are enough.

# Example only. Credentials stay as placeholders such as {{ apic_password }}.
# Four member ports on one leaf are illustrative, not a live inventory.
apic:
  access_policies:
    interface_policies:
      lldp_policies:
        - name: lldp_enabled
          admin_rx_state: true
          admin_tx_state: true
      mcp_policies:
        - name: mcp_enabled
          admin_state: true
      port_channel_policies:
        - name: lacp_active
          mode: active
          # NaC defaults also record min_links: 1 and max_links: 16.
          # Cisco APIC 6.1(3) and later can use 32 members on a port channel;
          # FEX and SAN port-channels remain at 16.
      spanning_tree_policies:
        - name: stp_bpdu_guard
          bpdu_guard: true
      storm_control_policies:
        - name: storm_control_edge
          action: drop
    leaf_interface_policy_groups:
      - name: Leaf101_PC
        type: pc
        aaep: LAB-AAEP
        lldp_policy: lldp_enabled
        port_channel_policy: lacp_active
        mcp_policy: mcp_enabled
        spanning_tree_policy: stp_bpdu_guard
        storm_control_policy: storm_control_edge
    leaf_interface_profiles:
      - name: Leaf101_PC_IntProf
        selectors:
          - name: eth1-1-to-4
            policy_group: Leaf101_PC
            port_blocks:
              - from_card: 1
                from_port: 1
                to_port: 4
    leaf_switch_profiles:
      - name: Leaf101
        selectors:
          - name: Leaf101
            node_blocks:
              - from: 101
                to: 101
        interface_profiles: [Leaf101_PC_IntProf]

3. Dual-homed across two leaves — vPC Interface Policy Group (not covered in detail)

If the server is dual-homed to two different leaves, a PC Interface Policy Group is the wrong object. That design needs a vPC Interface Policy Group (infraAccBndlGrp with lagT=node, NaC type: vpc) and a vPC pair (protection group) for those two leaves. Cisco’s Layer 2 guide describes the vPC workflow. The vPC group uses the same kind of policy fields as the PC group, plus that pair relationship. This note does not walk through vPC protection groups, peer-link or the interface wizard. The existing Interface Wizard for vPC page covers the GUI path.

# Dual-homing across two leaves is a vPC Interface Policy Group, not a PC group.
# type: vpc maps to infraAccBndlGrp with lagT=node. The two leaves must also
# be a vPC pair (protection group). This note does not cover that setup.
# See the Interface Wizard for vPC page for the GUI walk-through.
apic:
  access_policies:
    leaf_interface_policy_groups:
      - name: Leaf101_102_vPC
        type: vpc
        aaep: LAB-AAEP
        port_channel_policy: lacp_active
        lldp_policy: lldp_enabled
        mcp_policy: mcp_enabled
        # Remaining fields follow the PC Interface Policy Group.
        # The vPC pair itself is not collected in this example.
