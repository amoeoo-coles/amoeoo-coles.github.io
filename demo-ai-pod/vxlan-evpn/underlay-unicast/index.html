VXLAN EVPN

Underlay Unicast Routing

Fabric links, vPC, the distributed anycast gateway, IP addressing, and IGP versus eBGP.

Companion to the Cisco document Cisco Nexus 9000 VXLAN BGP EVPN Data Center Fabrics Fundamental Design and Implementation Guide (© 2024). Visible “lab” wording is renamed to “demo”. Source page-footer markings are omitted.

What the underlay must provide

The underlay network in a VXLAN BGP EVPN fabric is an IP-configured routed network that provides connectivity between the VTEPs so unicast traffic can be forwarded between them in VXLAN tunnels. Routing-protocol implementation requires IP addresses first, applied according to an addressing scheme for the physical and logical interfaces on the leaf and spine nodes. Once the routing protocols are up, they provide connectivity between VTEP logical interfaces, such as the loopbacks used as source and destination interfaces for VXLAN tunnels.

Underlay unicast routing design requires decisions on the network’s physical topology, the IP addressing scheme, and the routing protocol to run in the underlay.

Questions for physical topology include how many super-spine, spine, and leaf nodes are required; how many uplinks from each leaf to the spine and from the spine to the super-spine; and whether endpoints need to be multi-homed to VTEPs using vPC.

Questions for the IP addressing scheme include whether fabric interfaces will have numbered or unnumbered IP addresses; how many leaf nodes, vPC-domain switches, and spine nodes there are in total; how many VLANs are acting as default gateways; how many VRFs there are and whether you need to route between them; what network services such as DHCP or VXLAN OAM the VTEPs will require; and what roles the spine nodes will support (route reflector, rendezvous point, border spine, or border-gateway spine).

Questions for the underlay routing protocol include whether there is a preference to run a protocol already in production; whether introducing it will require staff training; whether multi-vendor or multi-platform support is required; whether dual-stack IPv4 and IPv6 support is required; whether fast convergence and maximum scale are required; and whether the protocol is easy to configure, operate, and troubleshoot.

Design decisions always involve trade-offs. Architects should prioritize each requirement documented during requirements gathering and develop a proposal that addresses as many as possible. High-priority requirements are mandatory for the applications hosted on the network and for operating the network.

In a Clos fabric every leaf is fully meshed to all spine nodes in a single site. Each leaf-to-spine link is a fabric interface. Links on VTEPs facing attached endpoints are host interfaces. Links attached to external devices such as edge routers and firewalls are external or service interfaces. Host, external, or service interfaces can be single-homed to one VTEP or multi-homed to two VTEPs in a vPC configuration.

Virtual Port Channel (vPC)

The data center hosts applications that need to be always available to users. Cisco Virtual Port-Channel (vPC) is a Layer 2 port-channel that allows endpoints to attach to two VTEP switches (multi-chassis) with both links in an active forwarding state. It was first introduced on Nexus 5000/7000 platforms and continues on Nexus 9000. The Nexus 9000 platform has two variations: standard vPC with a physical peer link, and vPC Fabric Peering (vPC without a physical peer link).

A VXLAN BGP fabric is a routed fabric. The underlay fabric interfaces between leaf and spine provide Layer 3 equal-cost multipath (ECMP) from a source to a destination IP address. In the data plane, vPC member switches behave like a single switch to endpoints attached to the vPC interfaces. To remote leaf switches sending traffic to an endpoint connected to a vPC member, the members are also seen as a single next hop using a common IP address called a vPC Virtual IP (VIP). The VIP is an anycast IP address configured on both vPC member leaf switches.

Each leaf is also a VTEP. Each VTEP’s tunnel interface is a Network Virtualization Edge (NVE) interface, bound to a dedicated loopback separate from the loopback used for the routing-protocol router ID. The NVE interface IP is the next hop to reach all tenant endpoints and networks attached to that VTEP. The NVE loopback is assigned a primary IP (PIP), unique to each vPC member, and a secondary IP that is the vPC VIP, an anycast address common to the members. The vPC VIP encapsulates all VXLAN traffic, including unicast and multicast. Cisco documentation commonly uses Loopback1 as the loopback bound to the NVE interface, but another loopback number can be used.

The following table summarizes when the vPC VIP is used as the next hop for host and prefix routes.

Loopback 0 is commonly used as the router-ID IP for underlay routing protocols such as OSPF and IS-IS. Those protocols automatically select a loopback as a router ID, but it is best practice to set the underlay IGP router ID manually to the loopback assigned for that purpose. The 32-bit router ID is usually set manually under the BGP process.

Separating the underlay-routing loopback from the VTEP NVE loopback provides stability during failure. The vPC consistency checker validates that both members have the same vPC-related configuration. Devices connected to the members receive the same LACP system ID when negotiating the vPC port-channel. If the checker shuts down the NVE interface by shutting down the NVE tunnel source, and the underlay routing protocol shares that same loopback, both the NVE interface and the underlay protocol go down. A data-plane configuration issue in the vPC system would then impact the underlay control plane. Separate the loopbacks by function to avoid this shared fate.

Each vPC leaf needs three IP addresses for these loopbacks: a unique IP for the underlay routing-protocol router ID, a unique primary IP for the NVE interface, and an anycast secondary IP for the NVE interface vPC VIP.

If the fabric interface between a leaf and one of the spines fails, traffic hashed to that leaf should have a path across the vPC peer-link to the peer switch so it can use that peer’s uplink. The vPC peer-link is a Layer 2 port-channel. An SVI is created on the members inside a VLAN that acts as a backup SVI for traffic redirection. That backup SVI extends the underlay between the members. Underlay unicast routing protocols such as IS-IS, OSPF, or eBGP must establish peering on the backup SVI. For BUM traffic and multicast routing, PIM sparse mode is enabled in the underlay. The underlay network is in the default VRF table.

The following image shows a configuration example of a backup SVI in VLAN 3999, with OSPF and PIM in the underlay. The vPC peer-link must allow VLAN 3999 on the port-channel trunk.

The vPC peer-gateway feature must be enabled on both peers to facilitate NVE RMAC/VMAC programming on both peers. For peer-gateway functionality, at least one backup routing SVI must be enabled across the peer-link and configured with PIM. This provides a backup routing path when a VTEP loses complete connectivity to the spine. Remote peer reachability is then rerouted over the peer-link.

Backup SVI VLANs are infrastructure VLANs: they are not mapped to VXLAN L2 VNIs. Define them with:

exus(config)# system nve infra-vlans <1-3967>

A separate Layer 3 routed interface between vPC member switches as a backup path is also supported. The underlay is extended on that routed interface.

The first advantage of a separate Layer 3 backup path is redundancy and fault isolation: a failure of the vPC peer-link will not impact backup-path traffic. Another advantage is that backup traffic does not compete with regular VXLAN or vPC synchronization traffic on the peer-link, so there is no risk of congestion from sharing that path. The disadvantage is that it consumes one extra physical interface.

Both architectures are supported. Key considerations include traffic engineering (routing policies or metrics so the backup path is used only during a failure, by adjusting OSPF, IS-IS, or eBGP); redundancy and failure detection (BFD or other mechanisms can help ensure quick failover); and operational complexity. A backup SVI over the vPC peer-link is simpler but might offer different fault tolerance and flexibility than a separate Layer 3 routed backup path. The latter might be more complex but is often preferred in large-scale, high-availability environments where traffic resilience and fault isolation are critical.

Distributed anycast gateway

In a VXLAN EVPN fabric, every VTEP is assigned the same MAC address for every L2 VNI SVI that acts as a default gateway. A common gateway MAC assigned across all VTEPs for all networks is a Distributed Anycast Gateway (DAG).

The DAG is a pervasive-gateway approach. A network shares the same gateway IP and the globally assigned DAG MAC address. In the figure, the VLAN 10 gateway IP and MAC are the same on leaf 1, leaf 2, leaf 4, and leaf 5. The DAG aligns with the peer-gateway capability in vPC, providing active/active forwarding without First Hop Redundancy Protocols (FHRP) such as HSRP or VRRP. Peer-gateway allows both vPC members to act as gateways for connected endpoints destined to the router MAC of the vPC switch, without sending the packet across the peer-link to the primary.

VLANs that leverage DAG are usually extended across VTEPs, allowing virtual-machine mobility. As an endpoint moves from one VTEP to another, the ARP entry for the gateway MAC does not need to be resolved again: the gateway MAC and IP remain consistent across VTEPs provisioned with the same VLAN.

In infrastructure IP planning, VLANs that require Layer 2 extension need a single shared gateway IP per VLAN and a common anycast gateway MAC across all VLANs. VLANs do not need to be connected to every VTEP. Place them on switches based on security, scale, traffic pattern, and application requirements.

The following guidelines must be followed when implementing vPC VTEPs in VXLAN fabrics:

  • Bind NVE to a loopback address separate from other loopbacks required by Layer 3 protocols. A best practice is a dedicated loopback for VXLAN and a separate loopback for Layer 3 underlay protocols.
  • The loopback used by NVE needs a primary IP address and a secondary IP address. The secondary IP is used for all VXLAN-encapsulated traffic, including multicast and unicast.
  • The primary IP is unique. The secondary IP on the loopback is necessary because interface NVE uses it for the VTEP IP address, and it must be the same on both vPC peers.
  • vPC peers must have identical VLAN-to-vn-segment mapping, NVE1 binding to the same loopback interface, the same secondary IP address, different primary IP addresses, and consistent VNI-to-group mapping.

If those configurations are inconsistent between the vPC members, the NVE loopback interface will be shut down administratively on the vPC secondary VTEP.

vPC Fabric Peering

Traditional vPC multihoming requires a physical peer-link between the members. A VXLAN BGP EVPN Clos fabric already gives each leaf a fully meshed connection through the spines, so if a leaf in a vPC has two spines it already has two physical paths to its vPC peer. The physical peer-link can be removed. In vPC Fabric Peering the peer-link becomes a logical vPC virtual peer-link. Two tunnels are created: a data-plane tunnel that carries VXLAN traffic, and a control-plane tunnel that syncs data-plane state such as ARP, MAC, and IGMP between the vPC leafs using Cisco Fabric Services over IP (CFSoIP). Traditional vPC with a physical peer-link uses CFS over Ethernet (CFSoE).

The virtual peer-link requires a source and terminating interface. A loopback is also required. That loopback cannot be the same as the peer keepalive or the loopback used for the VTEP IP address. The underlay unicast routing-protocol loopback (OSPF or BGP router ID) can be used, but the best-practice recommendation is a dedicated loopback for the virtual peer-link, for fault isolation. Keepalive can be out-of-band (mgmt0 or a dedicated interface) or in-band (a dedicated loopback over the fabric).

Control-plane requirements change slightly compared with traditional vPC:

  • The advertise-PIP and RMAC configurations are mandatory in vPC Fabric Peering if EVPN Type 5 is used with this feature. vPC and orphan Type 5 routes will be advertised with (PIP, RMAC).
  • An orphan Type-2 host is advertised using PIP and RMAC. A vPC Type-2 host is advertised using vPC VIP and VMAC.
  • Some platforms may require TCAM carving of the region ing-flow-redirect before configuring vPC Fabric Peering. TCAM carving requires saving the configuration and reloading the switch. Confirm the platform steps from the Nexus 9000 NX-OS VXLAN configuration guide.

The steps to configure vPC Fabric Peering on the vPC leafs are: define the vPC domain, then define the uplinks to the spine.

When defining the virtual peer-link, DSCP 56 is also applied for virtual peer-link traffic. The virtual peer-link synchronizes data-plane state; it is a control-plane tunnel and must be treated as high priority. The spine nodes must match this peer-link traffic and allocate it to the strict-priority queue during congestion:

//Classify traffic by matching the DSCP value (DSCP 56 is the default value).
class-map type qos match-all CFS
   match dscp 56

//Set traffic to the qos-group that corresponds with the strict priority queue for the
appropriate spine switch.
policy-map type qos CFS
   class CFS
      Set qos-group 7

//Assign a classification service policy to all interfaces toward the VTEP (the leaf layer
of the network).
interface Ethernet 1/1
   service-policy type qos input CFS

IP address design

Poor IP address design can cause control-plane scale challenges from a lack of summarization, risk of overlap and exhaustion from a lack of scheme, and poor allocation practice. A good scheme helps you understand the logical topology and troubleshoot quickly. Before defining a scheme, understand all the roles, places in the network, and protocols and services required on each device. Calculate the maximum IP addresses required per device role, leaving room for endpoint and node growth.

A leaf with endpoints attached needs the following for unicast routing:

  • Fabric-interface IP. Assigned as a point-to-point /30 or /31 on the physical interface, or as IP unnumbered borrowing from another interface such as a loopback. In VXLAN BGP EVPN fabrics, fabric interfaces borrow from the loopback allocated for the underlay IGP, commonly loopback 0. Unnumbered interfaces are best practice because they reduce the number of transit IP addresses between leaf and spine and simplify automation and allocation management.
  • Loopback interface IP. At least one loopback for Layer 3 underlay routing and one for the NVE interface. vPC and vPC Fabric Peering have additional requirements: Fabric Peering may need a unique loopback for the virtual peer-link or peer keepalive.
  • L2 VNI gateway IP. Every L2 VNI needs an SVI IP for the VLAN mapped to that VNI. That SVI IP is the gateway for hosts attached to the network.
  • Network infrastructure services. DHCP relay and VXLAN OAM are commonly used on VTEPs. Each VTEP needs a unique loopback in a VRF to identify the leaf for DHCP and OAM packet forwarding and receiving. SVI gateway IPs cannot be used because they are shared across all VTEPs by the distributed anycast gateway.

Border leaf or border-gateway devices need additional IP addresses to support their role. For those use cases, reference the Nexus 9000 NX-OS VXLAN configuration guide on cisco.com, particularly the chapters on Multisite VXLAN BGP EVPN and External VRF Connectivity.

A spine used only for unicast routing needs fabric-interface IPs (point-to-point /30 or /31, or unnumbered from loopback 0 — unnumbered is again best practice) and at least one loopback for Layer 3 underlay routing. If the spine is overloaded with border-gateway or border-spine functions, more IP addresses are required.

IGP versus eBGP underlay

VXLAN is the data-plane protocol that works with the MP-BGP EVPN control plane. MP-BGP has been used with Multiprotocol Label Switching (MPLS) for two decades, and the latest evolution of MPLS with Segment Routing continues to use MP-BGP. In MPLS networks, MP-BGP signals the exchange of VPN or overlay routing information. The largest MPLS networks use IGPs such as OSPF or IS-IS in the underlay for provider-edge connectivity through the core. The IGP’s function is fast ingress-PE to egress-PE connectivity. Core routers had no overlay routes unless they had a route-reflector or route-server role. That history is one argument for using an IGP as the underlay in a VXLAN BGP EVPN network as well.

Informational RFC 7938, “Use of BGP for Routing in Large-Scale Data Centers,” proposed using eBGP in a Clos fabric, with optimizations such as maximum-paths for ECMP and lowering Minimum Route Advertisement Interval (MRAI) timers so BGP behaves like an IGP. It is possible to create a very large-scale data-center fabric using eBGP. Whether it is worth tweaking BGP to behave like an IGP depends on the operational model. Some industries simplify systems by removing as many features as possible to avoid defects and reduce security attack vectors. Those reasons are valid but specific to the industry and operational goals; they do not apply to all sectors.

A vital concluding point on RFC 7938 is that it does not discuss or propose using eBGP as an underlay in a VXLAN BGP EVPN fabric, or any overlay running in the data center. Referencing that RFC is not a strong argument for using eBGP as an underlay in VXLAN BGP EVPN fabrics.

A fundamental design principle for any complex system is to break it into smaller functions. Overloading a single protocol like BGP to do underlay and overlay routing adds technical debt. Separating IGP for underlay and BGP for overlay allocates specialized functions to each protocol.

Cisco Nexus 9000 NX-OS fully supports VXLAN BGP EVPN fabrics with IGP and eBGP underlays. Cisco’s best practice is to use an IGP, such as OSPF or IS-IS, in the underlay with an iBGP EVPN overlay. Some industries prefer eBGP; NX-OS fully supports that as well.
