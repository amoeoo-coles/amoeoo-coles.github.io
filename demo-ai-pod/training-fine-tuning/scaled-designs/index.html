Scaled Designs, Validation and Next Steps

128, 256 and 512 GPU examples, power and racking, validation, NVIDIA certifications, and future extensions.

Companion to the Cisco Validated Design Cisco AI POD for Enterprise Training and Fine-Tuning Design Guide — Using Cisco UCS Dense GPU Platforms and Nexus 9000 Series Switches (Cisco Public, published January 2026). Visible “lab” wording is renamed to “demo”.

This chapter builds on the architectural building blocks and subsystem design to present complete AI POD solutions for various scale points. Each design in the source guide includes the required components, connectivity details, and a Bill of Materials (BOM) to guide planning and procurement. These prescriptive design options are then followed by the specific topology that was validated for this CVD.

Scaling AI POD Training Design Examples

To provide standardized and repeatable deployment patterns, this design defines three specific blueprints known as Scale Unit Types. Each type is designed to maximize the port density of a specific Nexus leaf switch pair used in the backend fabric, resulting in building blocks of 32, 64, and 128 GPUs when using the Cisco UCS C885A server. Enterprises can start with one of these pre-defined Scale Unit Types and then add more units over time to reach higher scale targets (for example, 256 or 512 GPUs).

The following design options are built using Scale Unit Type 3. This 128-GPU building block represents a relatively large starter cluster for many enterprises and provides a pathway for scaling to 512 GPUs without introducing a super-spine tier. A similar methodology can be applied to building clusters with the smaller 32- or 64-GPU Scale Unit Types.

AI POD design: 128 GPU cluster

Figure 35 shows a complete AI POD infrastructure design for a 128-GPU training and fine-tuning cluster, built using a single Scale Unit Type 3 as the foundational building block.

The design uses dedicated GPU backend and frontend fabrics. The frontend fabric provides connectivity for storage, management, and other services. It can be extended to support hybrid deployments with inferencing workloads in the future. The design can support either:

  • Cisco UCS C885A M8 servers (8 GPUs per node): This server supports 8 East-West NICs for the backend fabric and 1 or 2 North-South NICs for the frontend fabric.
  • Cisco UCS C845A M8 servers (up to 8 GPUs per node): This server supports a maximum of 4 East-West NICs (one for every two GPUs) and one North-South NIC, resulting in less connectivity and cabling compared to a UCS C885A deployment.

Power and Racking

The modular design allows enterprises to start with a right-sized infrastructure and scale as their AI initiatives grow. The high density of GPU servers means that power, cooling, and rack space are critical design considerations that must be planned for from the beginning.

Planning should account for the eventual scale of the cluster, as there are certain scale points where a design change can have a significant impact on the physical layout and cabling. In the AI POD architecture, scaling beyond 512 GPUs is one such inflection point.

The guide provides a sample rack layout for a 256 GPU cluster based on these assumptions:

  • Target Cluster Size: 256 GPU cluster, built using 2 × 128 GPU Scale Unit Type 3 clusters
  • Server: Cisco UCS C885A M8 Server with 8x H200 GPUs and 8 backend (1 × 400GbE) NICs and 1 frontend (2 × 200GbE) NIC
  • Rack Specification: 42 RU racks with 30 kW of power to each rack
  • Backend Fabric Design: 2-way rail-optimized (4 rails per switch)

Notes from the sample layout:

  • The first row shows the first Scale Unit Type 3 with 16 Cisco UCS C885A servers and the leaf pair it connects to, in both the backend and frontend fabric.
  • The second row shows the second Scale Unit Type 3. This will require the frontend connections to go from Row 2 to Row 1. From a cabling perspective, it would be easier to use a smaller port-density pair of frontend leaves in both Row 1 and Row 2 so that there is a pair of frontend leaves for each row (similar to the backend leaf pair).
  • Row 1’s middle rack includes both frontend and backend spine switches and the management UCS server, unlike Row 2, in addition to the backend (for Scale Unit Type 3) and frontend leaf switches for both rows, unless the 2 × Nexus 9364D-GX2A frontend leaf switches are replaced with 4 × Nexus 9332D-GX2B, a pair per row.
  • An out-of-band 1/10GbE Ethernet switch is not shown in the rack layout but could also be deployed in the middle rack. This can also be split across rows by adding a smaller port-density switch pair to each row.
  • Each server-only rack consumes ~12.5 kW × 2 = 25 kW of the 30 kW rack.
  • Row 1 (switch + management) as shown consumes: 4 × 3 kW (per N9364E-SG2) + 4 × 1.5 kW (per 9364D-GX2A) + ~1.5 kW (Cisco UCS X-Series with 3 Cisco UCS M8 control nodes) = ~20 kW. This allows for ~10 kW of space for storage if there is sufficient RU in this rack. Total rack space used by the gear in this rack is 23 RU (25 RU if an OOB management switch is deployed in this rack or if space is left between the gear for cabling). In a 42 RU rack, this leaves ~17 RU of space for storage and associated gear.

Note: The Cisco UCS X-Series chassis in the source power discussion is the management Cisco UCS with 3 servers (control plane).

NVIDIA Certifications

Cisco and NVIDIA have a strong partnership spanning platform compatibility and server certifications to comprehensive, full-stack reference architectures. Cisco has both NVIDIA “Certified” platforms and Enterprise Reference Architecture “Compliant” designs.

Key NVIDIA-Certified Cisco UCS platforms include:

  • UCS C845A with L40S, H200 NVL, and RTX Pro 6000 GPUs
  • UCS C885A with H100 and H200 GPUs

For a complete list, see the NVIDIA qualified system catalog. Beyond certifying individual servers, Cisco collaborates with NVIDIA on Enterprise Reference Architectures. These include a range of designs, starting from a 32 GPU cluster using a two-switch, 2-way rail-optimized network design to a 1k GPU cluster using a 3-tier, 8-way rail-optimized spine-leaf design.

NVIDIA’s criteria for an Enterprise RA “Compliant” design (at the time of writing of the guide) require:

  • Switching that supports Spectrum-X enablement for the East-West networking.
  • Spectrum-X enablement to be activated and licensed for the East-West networking.
  • Adherence to the relevant Spectrum-X RA design patterns such as a 4-leaf (2 rail/switch) HGX design.

Cisco Nexus 9000 Series Cloud Scale and Silicon One switches meet the above criteria. NVIDIA Enterprise RA documents cited by title (links are not publicly shareable and require NVIDIA Partner Portal access):

  • ERA-00003-001_v04 — NVIDIA HGX H100+H200+B200 8-GPU and NVIDIA Spectrum Platforms — 28 February 2025
  • ERA-00010-001_v01 — Network Deployment Guide NVIDIA SpectrumX Platforms — 4 July 2025

Future Extensions to AI POD

The architecture will continue to evolve and is designed to be extensible. The dedicated Management and Services Cluster can be expanded to include additional value-added services and eventually a Services Pod for a scaled deployment.

  • Cisco AI Defense: As models are fine-tuned, it becomes essential to analyze them for security vulnerabilities, data poisoning, or adversarial evasion techniques. Extending the management cluster to support a services cluster provides an isolated environment to run these security analysis tools post-fine-tuning before models are considered for production use. In a hybrid deployment with inferencing, AI Defense can provide run-time protection; a service cluster with proximity to the GPU cluster is necessary to secure the inferencing pipeline while providing the low-latency response it requires.
  • Cisco C880A M8 Server with B300 GPUs: A key future extension will be the integration of Cisco’s newest dense-GPU AI server, the Cisco UCS C880A M8. This next-generation platform combines NVIDIA’s Blackwell-based HGX B300 GPUs with Intel Xeon 6 processors to deliver a significant performance leap compared to previous generations, for both training and real-time LLM inference.

Conclusion

Cisco AI POD is a comprehensive infrastructure solution for enterprises, designed to support their AI/ML journey and a range of AI workloads from training to fine-tuning to inferencing. The solution detailed in this guide is a complete, integrated, and full-stack infrastructure specifically tailored for AI training and fine-tuning workloads. This architecture directly addresses unique AI requirements of enterprises, such as support for multiple smaller workloads with multi-tenancy, incremental scale with operational simplicity and consistency, and ease of integration into existing data center environments.

The solution includes GPU-dense compute (UCS AI platforms), high-performance networking (Cisco Nexus), storage from industry-leading partners, and a robust AI software stack running on Linux or Kubernetes. Each AI POD is built, integrated, and validated in Cisco demos, backed by Cisco Validated Designs, and provides solution-level support through Cisco TAC. While focused on core infrastructure today, Cisco AI POD solutions are designed to evolve, supporting advanced security solutions (Cisco AI Defense, Hypershield) and new technology trends.

By leveraging the modularity and flexibility of Scale Units (for example, 32, 64, or 128 GPU clusters), combined with operational ease, design simplicity, and incremental scalability, Cisco AI PODs ensure consistency across all deployment vectors, even at scale. This approach reduces time-to-value, lowers total cost of ownership, and empowers enterprises to confidently operationalize AI initiatives that bring value to the business.
