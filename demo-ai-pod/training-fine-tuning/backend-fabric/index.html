Training & Fine-Tuning

Backend Fabric Design

East-west fabric requirements, non-blocking Clos, rail-optimised connectivity, RoCEv2, and VXLAN EVPN multi-tenancy.

Companion to the Cisco Validated Design Cisco AI POD for Enterprise Training and Fine-Tuning Design Guide — Using Cisco UCS Dense GPU Platforms and Nexus 9000 Series Switches (Cisco Public, published January 2026). Visible “lab” wording is renamed to “demo”.

To meet the stringent demands of AI training and fine-tuning workloads, the backend fabric uses several technologies and optimizations to deliver lossless, low-latency, high-bandwidth, GPUDirect RDMA communication between GPUs in Cisco UCS nodes.

Non-Blocking Fabric

The fabric is designed to be non-blocking and uses 400GbE links end-to-end to provide full 400 Gbps of bandwidth from GPU-to-GPU, as illustrated in Figure 15.

The non-blocking fabric is achieved by ensuring that the aggregate bandwidth from the UCS nodes to the leaf switches equals the aggregate bandwidth from the leaf switches to the spine switches. The design shown is a 4-node Cisco UCS C885A cluster with eight GPUs and eight NICs in each node, with a total of 32 uplinks (4 nodes × 8 GPUs = 32 links) distributed across 2 leaf switches. This provides 1:1 oversubscription by matching the total number of downlinks from both leaf switches to the number of uplinks to the spine switches. Traffic between any two UCS nodes has the full 400GbE bandwidth across the fabric. The spine-to-leaf links can also use 800GbE (when using Scale Unit Type 3 and N9364E-SG2-O with OSFP transceivers) in preparation for 800GbE end-to-end when 800GbE NICs are available.

Quality of Service

For GPUDirect RDMA and RoCEv2 to deliver performant inter-node GPU-to-GPU communication, the fabric must provide a lossless environment. Any packet loss can have a significant impact on job completion times.

Cisco Nexus switches deployed in AI POD backend fabrics provide comprehensive QoS features to ensure a lossless Ethernet/IP fabric for RoCEv2, supporting both IP/BGP and VXLAN EVPN fabrics. Implementing QoS typically involves:

  • Marking the traffic at the edge (by endpoints typically)
  • Classifying and queueing the marked traffic across the fabric
  • Using congestion avoidance mechanisms to prevent input and output buffer overruns

To identify and prioritize RoCEv2 traffic and other critical traffic, appropriate QoS marking (primarily by GPU nodes) should be on all traffic incoming into the fabric. In an AI/ML backend fabric, the majority of the traffic is RoCEv2 data. Critical congestion notification traffic such as Congestion Notification Packets (CNP) generated by switches experiencing congestion also needs to be marked, classified, and prioritized to prevent packet loss.

Connecting UCS GPU Nodes to the Backend Fabric

Backend NICs should be configured as untagged access interfaces with an IP addressing scheme that allows the GPUs allocated to a given workload to communicate with optimal performance.

When GPUDirect RDMA is enabled, direct GPU-to-NIC data transfer uses the internal PCIe path. On Cisco UCS C845A, communication between GPUs located on different PCIe switches is routed through the CPU; 2-way and 4-way NVLink bridges are not recommended across CPUs for this reason.

The Cisco UCS C885A M8 server supports eight NVIDIA H200 SXM5 Tensor Core GPUs. Each GPU connects to four fully non-blocking NVSwitches within the node, enabling a high-speed NVLink bidirectional bandwidth of 900 GB/s between any pair of GPUs in the same node. For inter-node connectivity, each H200 GPU is also connected to a dedicated NIC (such as a ConnectX-7) via a PCIe Gen5 x16 interface.

The Cisco UCS C845A M8 server supports up to 8 PCIe GPUs of the same type (L40S, RTX PRO 6000, H100 NVL, and H200 NVL), with both 2-way and 4-way NVLink bridges. When using 2-way bridges, the bridge must be fully populated with GPUs (minimum of 2 adjacent GPUs); for 4-way bridges, a minimum of 4 adjacent GPUs are necessary per bridge.

Note: GPU deployment on Cisco UCS C845A should start with slot 8, with subsequent GPUs (must be in pairs) placed in adjacent slots for a total of 2, 4, 6, or 8 GPUs per node.

Rail-Optimized Design

A rail-optimized design is a specific network topology for connecting GPUs to the leaf switches, designed to provide low-latency and high-bandwidth GPU-to-GPU communication across multiple GPU nodes. In a rail-optimized topology, GPUs of the same rank across different nodes are connected using their East-West NICs to the same leaf switch. As nodes are added, this creates “rails” of GPUs of the same rank on the leaf or rail switch. This topology is optimized to maximize all-reduce performance, a critical collective communication operation used to synchronize gradients during distributed training.

Note: As model architectures evolve (for example, the Mixture of Experts model seen in more recent LLMs), the collective communication patterns may change. Also, the rail-optimized design assumes that all GPUs are part of a single large workload, which may not be the case in enterprise deployments.

NVIDIA’s Enterprise Reference Architecture for enterprise deployments of up to 1024 GPU clusters recommends a rail-optimized topology using at least two rail switches interconnected by direct links or through a spine or super-spine layer at higher scales.

Rail-optimized topology (2-way)

In the AI POD architecture, the UCS server GPUs and associated East-West NICs are typically distributed across the leaf switch pair in each Scale Unit Type. This configuration inherently results in a rail-optimized topology with multiple rails mapped to the same leaf (or rail) switch.

On a Cisco UCS C885A system with 8 GPUs and 8 East-West NICs (1:1 GPU:NIC ratio), the 2-way design results in each of the leaf switches having four rails. The rails on the same switch form a Rail Group (RG). Depending on how the rails are distributed, this could result in the first rail switch connecting rails [1,3,5,7] and the second connecting [2,4,6,8]. Communication within a Rail Group on a given switch is direct (single-hop) and does not require traffic to traverse the spine switches.

If NVIDIA PXN (PCIe × NVLink) is enabled, GPUs can also communicate across rails using NVLinks. PXN enables a GPU to communicate with another NIC on the same node through NVLink and then PCIe.

Rail-optimized topology (4-way)

At higher scales, as the number of leaf switches increases, the UCS servers can optionally be connected using a 4-way leaf design. The rail group consists of two rails per leaf switch across a total of four rail switches (representing 2 Scale Units), assuming an 8-GPU, 8 East-West NIC node such as the UCS C885A. This may result in the first rail switch hosting rails [1,5], the second [2,6], the third [3,7], and the fourth [4,8]. NVIDIA PXN can also be leveraged for efficient GPU communication across rails using NVLinks.

Rail-optimized topology (8-way)

The 8-way rail-optimized topology, commonly seen in large training clusters, uses eight leaf or rail switches to connect each GPU node. For 8-GPU, 8-NIC compute servers (for example, Cisco UCS C885A), this design results in a dedicated leaf switch per rail. For non-blocking connectivity through the spines, leaf switches may need to reserve up to half their ports for uplink connectivity. In a rail-optimized design, the rack layout will need to be carefully evaluated due to the any-to-any connectivity between the NICs in each GPU server and the eight rail switches.

Logical Architecture: VXLAN BGP EVPN

The spine-leaf topology can support either a pure Layer 3 or routed IP fabric (typically IP BGP) or an MP-BGP EVPN VXLAN fabric. The AI POD backend fabric uses MP-BGP EVPN VXLAN as it provides a flexible, standards-based, scalable architecture with the multi-tenancy that enterprises need. This architecture uses internet-scale MP-BGP in the control plane to advertise both Layer 2 MAC addresses and Layer 3 IP information. The EVPN control plane provides the network overlays to support multi-tenancy across an IP underlay. VXLAN provides the IP/UDP-based data-plane encapsulation for the overlay networks.

A key benefit is flexible support of both Layer 2 extension and Layer 3 forwarding with network isolation, allowing enterprises to share the training fabric across teams and workloads. The same combination of spine-leaf with VXLAN BGP EVPN is also used in the frontend fabric, providing operational consistency across both fabrics and, for enterprises already using this architecture, a unified design across AI and non-AI environments.

Multi-tenancy

Multi-tenancy enables multiple lines of business and teams (or tenants) to share a single AI cluster. Trust boundaries within an enterprise differ from the strict isolation required in public cloud environments. Since enterprise tenants are typically internal teams, the security model is likely to be less rigid than in a GPU-as-a-Service (GPUaaS) offering.

Note: This CVD is not intended as a GPU-as-a-Service (GPUaaS) design, which involves additional considerations such as orchestration and management. This document focuses solely on the foundational aspects of building a multi-tenant AI infrastructure.

Multi-tenancy at the network layer

VXLAN Network Identifiers (VNIs) provide Layer 2 isolation by creating unique network segments for each tenant’s broadcast domain. For Layer 3, Virtual Routing and Forwarding (VRF) instances create separate, isolated routing tables for each tenant on the network devices (VTEPs), enabling different teams to use overlapping IP address schemes without conflict. MP-BGP uses Route Distinguishers (RDs) to keep tenant routes unique and Route Targets (RTs) to control which routes are shared.

The design supports two primary overlay types:

  • A Layer 2 overlay extends a broadcast domain across the fabric. A VXLAN BGP EVPN fabric makes this efficient with features that minimize flooding, such as ARP suppression and BGP EVPN Type 2 routes to distribute MAC address information. All nodes, and specifically the East-West NICs on these nodes, must be in the same IP subnet.
  • A Layer 3 overlay is used when routing between subnets is required within a tenant’s environment. The recommended, scalable approach is Symmetric Integrated Routing and Bridging (IRB). Both ingress and egress VTEPs participate in routing. A dedicated Layer 3 VNI (L3VNI) for each tenant’s VRF handles inter-subnet traffic. IP prefixes are distributed using BGP as EVPN Type 5 routes. To enable access to shared resources such as storage, route leaking can be used between tenant VRFs and a shared storage VRF.

Multi-tenancy at the compute and GPU layer

  • Server-level allocation: One or more servers are assigned to a single team or workload. For fully loaded Cisco UCS C885A and C845A servers, a tenant receives all 8 GPUs on the server and uses the high-speed on-server interconnects such as NVLink — and potentially across rails if NVIDIA’s PXN is enabled.
  • GPU-level allocation: Groups of GPUs are assigned to different teams or workloads, likely in multiples of two (for example, 2, 4, 8 GPUs). If GPUs in these servers are interconnected by NVLink, additional mechanisms are needed to allow GPUs in the same tenant to communicate while blocking GPUs on different tenants. Fractional or sub-GPU allocation such as MIG is typically not necessary in training environments.

In a dedicated training and fine-tuning cluster, server-level allocation allows all jobs, however small, to be accelerated, resulting in a shorter JCT. In a mixed or hybrid environment that includes inferencing, right-sizing tenant workloads while ensuring efficient use of GPU resources can be more challenging.

Multi-tenancy with Kubernetes

Kubernetes mechanisms for isolated multi-tenant environments include namespaces, Role-Based Access Control (RBAC), Resource Quotas and Limit Ranges, Network Policies (requiring a compatible CNI plugin), Linux cgroups, pod security features (including OpenShift Security Context Constraints), node isolation using taints and tolerations, KubeVirt for hypervisor-level isolation, and Hosted Control Planes in OpenShift.

For server-level allocation, Kubernetes can use node labels, taints, tolerations, and hardware profiles so that only workloads from a given tenant with the corresponding toleration are scheduled on a dedicated node. For GPU-level allocation, when a pod is assigned specific GPUs, the underlying Linux OS uses cgroups to restrict the container’s visibility to only those physical devices, preventing NVLink peer-to-peer communication between GPUs allocated to different tenants on the same server. The orchestrator then injects the CUDA_VISIBLE_DEVICES environment variable into the container.

IP Addressing

The addressing plan must support both the physical network infrastructure (the underlay) and the logical tenant networks (the overlay). Enterprise AI training clusters are relatively small, typically less than 1024 GPUs, and are isolated environments with no outside connectivity, so the IP addressing can be a private RFC 1918 block.

The VXLAN EVPN underlay provides IP reachability between the Cisco Nexus switches. The addressing scheme is straightforward, static, and completely independent of any tenant workloads — typically /30 for point-to-point links between switches and /32 for loopbacks. The overlay should be allocated a single, large IP block based on the maximum number of GPU endpoints the cluster is expected to grow to. MP-BGP EVPN allows overlapping address space across tenant VRFs, but in a dynamic enterprise environment this provides less flexibility and makes it harder to manage and troubleshoot.

  • Single-tenant with single or multiple large workloads: A single large IP subnet (for example, a /21) is allocated for the cluster, providing enough addresses for all GPU NICs. Smaller clusters can use a Layer 2 overlay. If the tenant has multiple workloads, the larger IP block can be segmented.
  • Per-tenant subnet model: Each tenant is assigned a dedicated IP subnet from the main block based on the number of GPUs allocated, with room for growth.

Note: When using Layer 2 forwarding in the overlay, it is important not to exceed the ARP cache for the OS running on the GPU nodes.

A sample overlay addressing scheme for scaling from 32 GPUs to 1024 GPUs in increments of 32 GPUs (Scale Unit Type 1) is shown in Table 11. For 1024 GPUs, a minimal IP subnet allocation of /21 or higher is required. The cluster IP block in the example is 10.11.0.0/16. Each Cisco UCS C885A needs as many East-West IP addresses as GPUs; each Cisco UCS C845A needs half as many (GPU:NIC of 2:1).
